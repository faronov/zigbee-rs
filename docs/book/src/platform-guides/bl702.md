# Bouffalo BL702

The XT-ZB1 sensor is a pure-Rust BL702 path. It does not link Bouffalo's
`liblmac154.a`, `libbl702_rf.a`, or another vendor radio archive.

## Layering

```text
environmental Sleepy End Device profile
        ↓
products/bl702-xt-zb1
        ↓
boards/bl702-xt-zb1
        ↓
bl702-hal + Bl702RadioPhy + SoftMacCore
```

`examples/bl702-sensor` is the short composition root.

The board returns typed I²C, SPI/USB, ADC, flash, power, PWM, UART, AES, and
other-pin resources. The product owns identity, the environmental profile,
battery/reporting policy, the protected persistence window, and linker map.

The composition root retains unused resources so ownership remains explicit,
then constructs:

```rust,ignore
SensorSedParts {
    wake: Bl702Wake::new(),
    status: NoStatus,
    environment: BlockingEnvironment::new(SyntheticEnvironment::new()),
    battery: BlockingBattery::new(SupplyBattery::new(adc)),
    ota: Bl702OtaLifecycle::new(channel, bl702_hal::pm::software_reset),
    actions: product::policy::USER_ACTIONS,
    supervisor: Bl702Supervisor,
    diagnostics: Bl702Diagnostics,
}
```

The product selects `Idle` for both fast (250 ms) and slow (10 s) parent-poll
waits. An `Idle` wait:

1. disables M154 receive and waits (bounded) for the M154 state machine to
   report idle; if it does not, the wait returns `WakeReason::Activity`
   instead of sleeping;
2. awaits an Embassy timer, so the executor executes WFI;
3. wakes on the TIMER channel 0 comparator-0 interrupt (CLIC source 52,
   CLIC direct mode `mtvec = entry | 0b10`).

Clocks, the RF analog block, PLL, and per-die calibration stay powered, so
there is no restore step: the next MAC RX/TX starts from the same idle state
used between ordinary operations. The time driver arms the comparator for
the earliest deadline, capped at 30 minutes so the 1 MHz counter's 64-bit
extension never misses its ~71.6-minute wrap. A boot self-test proves alarm
interrupt delivery; on failure the driver reverts to the previous polling
executor and diagnostics report `wfi=false`.

`Retention` (PDS/HBN) is rejected by the wake controller and refused by
`bl702_hal::pm`; no PDS/HBN behavior is claimed. Idle sleep was validated on
one XT-ZB1 against ZHA: the alarm self-test passes (`wfi=true`), Idle waits
show no radio vetoes, and fresh join, interview/reconfigure over the 10 s long
poll, Mgmt_Leave and reset/resume all work. Current draw and behavior across
the ~71.6-minute counter wrap are not yet measured.

## Radio and security

The direct-register path implements:

- per-die ACAL, KCAL, ROSCAL, and RCCAL;
- channel selection, energy detect/CCA, RX, and TX;
- the shared `SoftMacCore<Bl702RadioPhy>` MAC (software ACK and address
  filtering; the former FFI-backed `Bl702Mac` was removed);
- token-owned SEC_ENG AES with two startup KATs.

Production fails closed if hardware AES installation fails. It does not fall
back to software AES.

## Role images

`examples/bl702-sensor` follows the role template (one bin per role; see
"Role template" in the Soft-MAC porting guide):

| bin | features | MAC | build (release, `production`) |
|---|---|---|---|
| `bl702-sensor` | default | `Bl702SoftMac` (software ACK, polling receive) | 219,664 B flash, 16,590 B `.bss` |
| `bl702-ed` | `--features ed --bin bl702-ed` | `Bl702SoftMac`, `EndDevice` | 192,016 B flash, 26,188 B `.bss` |
| `bl702-router` | `--features router --bin bl702-router` | `Bl702RouterMac` = `SoftMacCore<Bl702ParentRadioPhy, Parent<8, 8, 0>, 8>` | 310,288 B flash of the 482,304 B primary slot; 42,068 B `.bss` + 592 B `.data` of the 72 KiB − 64 B RAM1 region (30,976 B free below the stack guard) |

The stack lives in its own 24 KiB RAM2 region (`0x42026000..0x4202C000`)
in every image, so the router's tables (`ZigbeeDevice<_, Router>` and the
16 KiB task arena) do not reduce it. The router's main task measures 4,568 B
(`-Zprint-type-sizes`).

**Stack budget.** Until the `bl702-router-stack` change the stack was 15 KiB.
A hardware stack paint of the 988f74e router (lab build, resume, reboot,
secure rejoin, relaying, ZHA Identify and Basic reads) measured a
**17,764 B peak**, 2,404 B below the 15 KiB region, on the one-shot boot
composition (`TaskStorage::poll` → `compose` → `DeviceBuilder` →
`NwkLayer::write_into` → `NeighborTable::new`); later traffic never went
deeper. The overflow ran into unused RAM below the stack, so nothing failed
visibly. The static worst case is the commissioning scan (`attempt_start` →
`nlme_network_discovery` → MAC scan): 20,720 B including the entry and
interrupt frames. That path was not exercised by the measurement. The
default sensor image's static worst case (20,288 B) also exceeded 15 KiB.

The application layout (`products/bl702-xt-zb1/link/memory.x`) therefore
reserves:

- a 24 KiB stack (measured peak + 6,812 B; static worst + 3,856 B), still
  below the reset-time memory window (top 16 KiB unused);
- a 64-byte guard (`_stack_guard_start.._stack_guard_end`,
  `0x42025FC0..0x42026000`) immediately below the stack, between `.bss` and
  the stack;
- linker `ASSERT`s that the guard is directly below a ≥24 KiB stack, that
  `.data`/`.bss`/`.uninit`/heap end at or below the guard, and that the stack
  stays below `0x4202C000`.

`product::stack_guard` arms the guard first thing in `main` and checks it
from the router/End Device run loop, before every sensor idle wait, and
before every flash erase/program (`storage::MainFlash` =
`GuardedFlash<XipFlash>`). A damaged guard masks interrupts and halts, so no
flash write or transmission runs from corrupted RAM. The guard only detects
an overflow.

`tools/bl702-stack-gate.py` with `tools/bl702-{sensor,ed,router}-stack-gate.args`
enforces the budget in CI from each release ELF:

- the layout;
- entry + task poll + CLIC trap + handler ≤ stack − minimum gap (3 KiB for
  the router, 4 KiB for the others);
- a 4 KiB frame cap with reviewed one-shot boot exceptions;
- per-path chain budgets.

It is a direct-call heuristic. The hardware stack paint remains the
authoritative evidence.

**Router ACK and Frame Pending.** A core-sent Imm-Ack is too late for a
parent, so the router uses `zigbee_mac::bl702::parent_phy`: the M154 sends
every Imm-Ack in hardware (address filter `PAN << 16 | short` plus the
extended address, auto-ACK on whenever the core installs a filter) and takes
Frame Pending from its own 32-entry source table, which the core programs
through `RadioPhy::set_ack_frame_pending`. The core's software pending table
is zero-sized (`PENDING = 0`), so the hardware is the only FP owner. A
source missing from the table gets FP=1 (vendor `lmac154` semantics), so a
full table and extended-source association polls err towards a short extra
receive window, never towards stranded data. The receiver stays on between
MAC operations; `M154_IRQ` copies every completed frame into a 4-entry ring
so a hardware-acknowledged frame is not overwritten. The end-device images
keep the hardware-tested polling path unchanged.

**Router persistence.** The router has no Zigbee OTA client, so its child
and APS journals use the top of the secondary slot below the trailer sector
(`0xF9000..0xFB000` and `0xFB000..0xFD000`); the security journal at
`0xFE000` is shared by every role with role tags `0x5201` (router) and
`0x5202` (ED). A future router OTA must cap staging at `0x72000` B or move the
journals. The SED's OTA writer may overwrite them after a reflash to the
SED; the role tag stops a later router from resuming that network state.

The role images are build-, clippy-, symbol- (`check-role-symbols.sh`) and
host-tested only (FPT, receive ring and completion-bit logic); see the
hardware gates below.

## Persistence and flash layout

`products/bl702-xt-zb1/layout` is the single source of the flash map; the
linker scripts, the loader, the application and `tools/bl702_ota.py` are
checked against it:

| physical | XIP | contents |
|---|---|---|
| `0x00000..0x01000` | | boot ROM header (BFNP) of the loader, `img_start` 0x2000 |
| `0x02000..0x0FFE0` | `0x23000000` | `bl702-xt-zb1-boot` loader |
| `0x0FFE0..0x10000` | `0x2300DFE0` | LoaderInfo record |
| `0x10000..0x87000` | `0x2300E000` | primary slot: MCUboot header 0x100, application at `0x2300E100` |
| `0x87000..0xFE000` | | secondary slot (OTA download) |
| `0xFE000..0x100000` | | `SecurityStateJournal` |

The ROM maps XIP linearly from `img_start` (`xip = 0x23000000 + phys -
0x2000`), so the overwrite-only design needs no SF_CTRL remap. The loader's
ROM-hashed image must end before `0xFFE0` because `bflb-mcu-tool` rounds
`img_len` up past the raw image; the LoaderInfo record is placed outside it.

The board owns the physical XIP flash resource. The product shares it
between two restricted views: the two-sector security journal, and the OTA
writer, which can erase/program only the secondary slot. Journal commits and
reset/resume run on one XT-ZB1 (commit `6926796`); power-loss recovery is not
yet tested.

## Bootloader and OTA

The loader (`products/bl702-xt-zb1/bootloader` over
`bootloaders/bl702-boot`) ports the CC2340 overwrite-only loader to the BL702
ROM flash routines and the shared `mcuboot-image` engine. On a pending
upgrade it validates the secondary image (SHA-256, ECDSA P-256, no
downgrade), copies it into the primary slot, re-validates, and clears the
request; a power loss during the copy restarts it from the intact secondary.
It then validates the primary, checks that its entry is `0x2300E100`,
invalidates the L1C cache, masks interrupts and branches to the
application's riscv-rt `_start`. Without a valid image it reports on the
UART and halts. It is about 14 KiB.

The application's OTA lifecycle is a port of the CC2340 flower's: OTA
identity manufacturer `0x1234`, image type `0x0702`, file version
`0x25MMmmpp` from the product's Cargo version; first query 300 s after boot
and then daily; 48-byte blocks; 120 s of fast polling around OTA traffic;
offers declined unless the loader trusts the application's key. After
verification it checkpoints the security state, writes the upgrade request
and resets through the ROM `GLB_SW_POR_Reset`.

The signing key stays outside the repository (`$BL702_OTA_KEY`, else
`~/.flower-keys/flower-own-ec-p256.pem`); only its public X‖Y is built into
the loader and the application. CI signs with a per-run key.

## Measurements

Temperature and humidity are synthetic. Battery uses the internal VBAT/2
GPADC path with eFuse gain trim and an explicit fallback for implausible
initialization/conversion.

## Build

Use `nightly-2026-03-23`:

```bash
python3 -m pip install --require-hashes --no-deps \
  -r tools/bl702-image-tool/build-requirements.txt
python3 -m pip install --require-hashes --no-deps --no-build-isolation \
  -r tools/bl702-image-tool/requirements.txt
python3 -m pip install imgtool==2.4.0
cd examples/bl702-sensor
./build-image.sh
```

The default is the production hardware-AES image. For the full UART trace:

```bash
BL702_DIAGNOSTIC_LOG=1 ./build-image.sh
```

The script writes to `target/riscv32imc-unknown-none-elf/release/ota/`:

- `bl702-xt-zb1-<label>-<ver>-full.bin`: program once at `0x0`; it covers
  `0x0..0x87000` and leaves the journal intact;
- `bl702-xt-zb1-<label>-<ver>-signed.bin`: the MCUboot image;
- `1234-0702-<file version>-…zigbee`: the Zigbee OTA file.

`BL702_OTA_VERSION_OVERRIDE=0.1.1` (test only) builds an otherwise
identical image with a higher version for a bench OTA. Serve `.zigbee`
files to ZHA with the zigpy local provider: `python3 tools/bl702_ota.py
index --output index.json FILE.zigbee`, then

```yaml
zha:
  zigpy_config:
    ota:
      extra_providers:
        - type: zigpy_local
          index_file: /config/zigpy_ota/index.json
```

Current production / diagnostic sizes:

| artifact | production | diagnostic |
|---|---:|---:|
| raw application | 228,208 | 298,584 |
| signed image | 228,615 | 298,992 |
| margin to the 0x76000 image limit | 254,713 | 184,336 |
| loader ROM image | 22,272 | 22,272 |

The release tool checks the official boot-header magic, the 32 MHz XTAL
clock selection, header CRC, image hash, the loader's key id and the
application entry. CI additionally checks the slot size, `_start` at
`0x2300E100` (application) and `0x23000000` (loader).

## Hardware status

The current artifacts are build/package/layout-tested in CI. One XT-ZB1 has
produced hardware evidence for:

- cold radio calibration;
- channel selection, CCA/ED, RX/TX;
- steering and association on channel 15;
- indirect polling and Transport-Key reception;
- ZHA interview, Configure Reporting, TCLK exchange, and live reports;
- security-journal replay commits and reset/resume (commit `6926796`);
- `Idle` sleep: alarm self-test (`wfi=true`), join, interview and
  reconfigure over the 10 s long poll, Mgmt_Leave and reset/resume (commit
  `7783588`);
- boot through `bl702-boot` and a signed v0.1.0 → v0.1.1 OTA over ZHA
  (~33 min, 299 KB), resumed after a server abort, installed by the loader,
  with the network resumed without rejoining (commit `8aeee49`).

Still open:

- power loss during the loader copy and during journal writes;
- P-256 verify time at 32 MHz;
- GPADC battery accuracy;
- `Idle` sleep current and long-poll stability across a 71.6-minute counter
  wrap;
- PDS/HBN low-power modes (not implemented);
- RF output/spectral qualification;
- hardware address filtering and auto-ACK integration;
- router (`bl702-router`): the auto-ACK enable bit, address/FPT register
  encodings and FPT miss semantics, frame-completion status bits, RX re-arm
  after a hardware ACK, the `M154_IRQ` CLIC source, PAN `0xFFFF` filtering
  before join, Imm-Ack timing and FP correctness in a capture, child
  polling and routing with a real child; the always-on `bl702-ed` image has
  no hardware run either.
