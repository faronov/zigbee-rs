# BL702

Bouffalo Lab's BL702 is an RV32 SoC with a shared BLE 5.0 and IEEE 802.15.4
radio. zigbee-rs contains a direct-register Rust radio for BL702/BL706 that
does not link Bouffalo's `liblmac154.a` or `libbl702_rf.a`.

The backend and a complete sleepy Zigbee sensor have been validated on an
XT-ZB1 against Home Assistant ZHA.

## Architecture

```text
Bl702RadioPhy
|-- digital PHY reset
|-- analog RF defaults
|-- per-die live calibration
|-- M154 polling CCA / TX / RX
`-- RadioPhy
        |
        v
SoftMacCore<Bl702RadioPhy>
        |
        v
zigbee-rs NWK / APS / ZDO / BDB / ZCL
        |
        v
XT-ZB1 temperature / humidity / battery endpoint
```

Frame construction, CSMA retries, software ACK matching, association, and PIB
state are provided by the shared `SoftMacCore`. The upper Zigbee layers are
the same Rust implementation used by the other platforms.

## Clean-room RF port

Public BL702 material documents clocks and ordinary peripherals but not the
M154 FIFO/register interface or the analog calibration order. The port was
reconstructed from symbols, machine code, and retained DWARF in Bouffalo's
distributed BL702 radio objects.

Cold boot runs:

1. Digital BZ PHY reset and default field programming.
2. Analog RF default programming.
3. ACAL at 2410, 2430, 2450, and 2470 MHz.
4. KCAL at 2402 and 2480 MHz, followed by table interpolation.
5. ROSCAL over gain indices 6-15 and two bandwidth settings.
6. RCCAL using 256 packed I/Q samples.
7. M154 initialization, channel selection, and TX-power setup.

The 1 KiB calibration sample RAM at `0x42024000` is preserved. Hardware polls
are bounded, so failed calibration returns `PhyError::Hardware` instead of
hanging forever.

## Hardware validation

### Raw radio

On the XT-ZB1, the direct-register backend completed cold-start calibration,
reported changing energy-detect values, received live Zigbee frames, and
completed repeated transmissions.

An independent Nordic 802.15.4 sniffer captured the exact probe frame:

```text
00 80 78 34 12 78 56 ff 0f 00 00 7a 69 67 62 65 65 2d 72 73
```

The capture reported RSSI -43 dBm and LQI 200.

### Full Zigbee sensor

The sensor read its factory identifier as IEEE address
`7c:b9:4c:61:92:3a:00:00`, discovered PAN `0xDFE9` on channel 15, associated
through parent `0xBA0F`, and received short address `0xFE33`.

The validated commissioning path included:

- association ACK and indirect Transport-Key delivery;
- secured Device_annce;
- Node Descriptor, Active Endpoints, and Simple Descriptor responses;
- Basic and Power Configuration attribute reads;
- Configure Reporting for clusters `0x0001`, `0x0402`, and `0x0405`;
- Trust Center link-key request, Verify-Key, and Confirm-Key;
- `CommissioningComplete { success: true }`;
- temperature, humidity, battery, and Identify entities in Home Assistant.

The current application still publishes synthetic temperature and humidity
values because no physical environmental sensor has been selected and wired.
Battery reporting samples the internal VBAT/2 GPADC path, applies the
factory eFuse gain trim, and logs an explicit synthetic fallback if
initialization or conversion is implausible.

The BL702 on-chip TSEN path is not a production capability. A lab-only attempt
on one XT-ZB1 returned implausible readings with both the pure-Rust code and the
official Bouffalo SDK. The archived source and findings are in
`tools/bl702-lab/experiments/tsen/`; validation is blocked pending a second
BL702 sample.

### Network persistence

`products/bl702-xt-zb1` owns a bounded 8 KiB security partition at physical
flash offsets `0xFE000..0x100000`. It wraps the board's 1 MiB XIP flash in two
4 KiB sectors and constructs `SecurityStateJournal`, so network credentials,
parent identity, and crash-safe outgoing counter reservations survive reset.
The sensor uses the durable start/resume, incoming-frame, tick, secured-rejoin,
leave, and factory-reset paths.

The partition is above the product's 512 KiB linked XIP window and therefore
cannot overlap the firmware image. The integration and partition bounds are
host-tested and RV32IMC-compiled. Actual sector erase/program and power-cycle
resume have not yet been exercised on the XT-ZB1, so persistence is not yet
claimed as hardware-proven.

## Rust target and memory

Use `riscv32imc-unknown-none-elf`, not `riscv32imac`. The tested BL702 does not
execute RV32A atomics; an atomic compare-and-swap generated by the IMAC target
caused an illegal-instruction trap during early startup.

```text
FLASH : 0x23000000, 512 KiB
RAM1  : 0x42014000, 80 KiB   (data, BSS, 16 KiB Embassy task arena)
RSVD  : 0x42028000, 1 KiB
RAM2  : 0x42028400, 15 KiB   (initial stack)
UNUSED: 0x4202C000, 16 KiB   (reset-time embedded-memory window)
```

Keeping the stack below `0x4202C000` avoids the reset-time `em_sel` embedded
memory window. The release profile uses a 16 KiB Embassy task arena; the
default 4 KiB arena cannot spawn the full Zigbee task.

## Build

```bash
rustup default nightly
rustup component add rust-src llvm-tools-preview
python3 -m pip install bflb-mcu-tool==1.10.0 pyserial

cd examples/bl702-sensor
./build-image.sh
```

The script creates an ELF, raw XIP payload, and a bootable flash image under:

```text
target/riscv32imc-unknown-none-elf/release/
```

The current production hardware-AES sensor is 176,930 bytes as a raw XIP
payload and 185,136 bytes as a packaged flash image. `--pllclk=Manual` keeps
the boot header on the 32 MHz XTAL used by UART, timer, and calibration delays.
The scripts isolate
`bflb-mcu-tool` because version 1.10.0 persists generated clock settings in its
installed package and `Manual` alone does not reset a previous 144 MHz
selection. Every packaged image is rejected unless its boot header explicitly
selects the 32 MHz XTAL.

## Flash and monitor

Connect the XT-ZB1 CH340 port (VID:PID `1A86:7523`), hold BOOT/GPIO28, and run:

```bash
cd examples/bl702-sensor
./flash.sh
```

The script auto-detects the serial port, resets through CH340 RTS, and verifies
that `bflb-mcu-tool` reports `[All Successful]`. Release BOOT and run:

```bash
./monitor.sh
```

The monitor resets through RTS and opens UART0 on GPIO14/GPIO15 at 2 Mbaud.
DTR is not connected to BOOT on the tested board, so entering ROM download
mode still requires holding BOOT during reset.

## API

```rust,ignore
use zigbee_mac::bl702::radio_phy::{Bl702RadioPhy, Bl702SoftMac};
use zigbee_mac::{MacPib, SoftMacCore};

let phy = unsafe {
    Bl702RadioPhy::initialize(|microseconds| board_delay_us(microseconds))?
};
let pib = MacPib::new(factory_ieee_address(), 0, 0);
let mac: Bl702SoftMac = SoftMacCore::new(phy, pib)?;
```

`Bl702RadioPhy::initialize` is unsafe because the firmware must provide
exclusive radio access, valid clocks, and an accurate blocking microsecond
delay.

## Peripheral HAL status

`bl702-hal` now provides:

- typed GPIO plus `embedded-hal` digital traits;
- blocking I2C0 and SPI0 buses;
- GPADC GPIO channels and the internal VBAT path;
- shared-controller PWM;
- UART0/UART1 and the free-running timer used by the production firmware;
- eFuse chip-ID access;
- a token-owned SEC_ENG AES-128 ECB single-block accelerator (`bl702_hal::aes`);
- XIP flash read/program/erase through the BL702 mask-ROM API, implementing
  the `embedded-storage` NOR traits;
- an explicit power API that rejects PDS/HBN instead of claiming an unproven
  wake path.

The [Bouffalo Lab Config Wizard](https://dev.bouffalolab.com/media/config/index.html)
provides an additional official cross-check for the GPIO-function matrix and
clock tree. Its I2C even/odd routing, SPI signal slots, PWM channel mapping,
and GPIO-to-ADC table match the routes encoded by this HAL.

`boards/bl702-xt-zb1` owns the chip resources once and splits them into runtime
resources (UART, timer, eFuse) and application resources (GPIO, buses, ADC,
PWM, flash, and power). The XT-ZB1 routes UART0 to GPIO14/GPIO15, I2C0 to
GPIO4/GPIO3, and the diagnostic SPI0 bus to GPIO7/GPIO8/GPIO9.

The HAL has 32 host tests and is compiled for `riscv32imc-unknown-none-elf`
with warnings denied. The generated image is also scanned for `amo*`, `lr.*`,
and `sc.*` instructions. UART, timer, eFuse, and RF remain hardware-proven.
The new GPIO, I2C, SPI, ADC, PWM, and destructive flash paths are not yet
silicon-tested.

The BL702 packet controller accelerates single reads/writes and the common
one-to-four-byte register-address write/read shape. Other valid
`embedded-hal` transaction lists use a bounded open-drain GPIO fallback so
adjacent operations and alternating directions retain the required repeated
START semantics.

Flash programming and erase execute from RAM, preserve interrupt/AES state,
flush L1 cache, reject XIP-backed source buffers, and validate physical
ranges. The sensor now uses these operations through the product-owned
security journal; the resulting image must be validated cautiously on XT-ZB1
before persistence is described as hardware-proven.

## Hardware AES backend

The BL702 production composition always enables the low-level
`zigbee-mac/hardware-aes-bl702` feature. The SEC_ENG AES-128 accelerator serves
every Zigbee CCM* and AES-MMO operation, replacing the RustCrypto software
core in the standard `cargo build --release` image.

Ownership flows through the composition root: the board surfaces the exclusive
`bl702_hal::peripherals::Aes` token as an application resource, and the sensor
hands it to `Bl702RadioPhy::install_aes_engine`, which constructs the
`AesEngine`, runs two back-to-back AES-128 known-answer tests (a re-key/reuse
cycle), and only then installs it. `SoftMacCore` delegates
`ForwardAesProvider::forward_cipher` to the phy, so NWK/APS CCM* and AES-MMO
key derivation run on hardware with no protocol-layer change. A missing engine
traps loudly instead of silently falling back to software, and every hardware
error is a bounded timeout — no unbounded spin.

`MacCapabilities.hardware_security` remains `false`: the Rust stack still
performs Zigbee security itself and only obtains a hardware block-cipher
provider, not autonomous MAC-level security offload. (The legacy `Bl702Mac`
FFI backend's `hardware_security` was corrected from `true` to `false` for the
same reason.)

The SEC_ENG AES register contract is transcribed from the open-source Bouffalo
`bl_iot_sdk` driver (`bl702_sec_eng.c` / `sec_eng_reg.h`) and cross-checked
against a FIPS-197 vector; see `bl702_hal::aes` for the full evidence trail.
Unlike the register-fed TLSR8258 block, this engine is memory/DMA driven
(`MSA`/`MDA`), so the driver uses word-aligned scratch buffers, explicit
RISC-V CPU/device memory fences, and volatile destination reads. Both startup
KATs pass on XT-ZB1 silicon. The hardware image then reaches periodic radio
operation and has completed a full secured ZHA commissioning flow including
Transport-Key, Device Announcement, descriptors, binding, Configure Reporting,
Trust Center link-key exchange, and encrypted temperature/humidity reports.
The conservative bounded-wait value is not cycle-characterized, and a silent
reset/resume capture remains pending. A startup mismatch still rejects the
engine rather than corrupting Zigbee security.

CI verifies the standard image drops every `aes::soft::fixslice` symbol, links
the `HardwareAes128`/`bl702_hal::aes` backend, and passes the RV32A,
vendor-symbol, XIP-placement, and size-budget gates.

## Known limitations

- Flash-backed network and security persistence is integrated, but sector
  erase/program and reset-resume still need cautious XT-ZB1 hardware
  validation.
- Temperature and humidity are synthetic until a real sensor is integrated
  with the new I2C API. The GPADC battery path applies factory gain trim but
  still needs hardware validation; dynamic offset calibration is not yet
  implemented.
- New GPIO, I2C, SPI, ADC, PWM, and destructive flash paths still need
  hardware validation.
- SEC_ENG AES commissioning and secured traffic are hardware-proven. Silent
  reset/resume and a cycle-derived bounded-wait value remain pending.
- PDS and HBN remain unavailable until radio, clock, flash, timer, and wake
  restoration are proven together.
- M154 operation and the executor are polling-only.
- Hardware address filtering and hardware auto-ACK are disabled.
- Occasional MAC `NoAck` retries were observed, although association,
  interview, security commissioning, and ZCL reports completed.
- RF output power and spectral behavior require lab measurement before
  production use.
