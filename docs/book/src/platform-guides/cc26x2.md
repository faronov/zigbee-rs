# TI CC26x2 / CC13x2 (CC2652P, CC2652P7)

zigbee-rs runs on the CC26x2/CC13x2 family (Cortex-M4F, 48 MHz) with a
pure-Rust HAL: no TI driver, RTOS, RF driver, MAC or Z-Stack is linked. The
system CPU drives TI's RF core firmware through its command doorbell and the
shared `SoftMacCore` provides every MLME/MCPS procedure.

```text
examples/cc26x2-router        composition roots: cc26x2-router, cc26x2-lab
products/cc26x2-dongle        identity, TX power, memory map, journals, CCFG
boards/cc26x2-dongle          wiring: UART0 DIO12/13, BSL DIO15, LF crystal
zigbee-mac::cc26x2            Cc26x2RadioPhy (FullTx, RF core auto-ACK)
cc26x2-hal                    trim/clocks, RTC time driver, UART, TRNG,
                              flash (ROM), CCFG builder, RF core driver
```

## Start-up

`cc26x2_hal::setup::trim_device()` is driverlib `SetupTrimDevice()` (SDK
8.33.00.16). The factory trims, cache mode, XOSC_HF and LF-clock helpers are
the boot ROM's driverlib table entries, the same code TI's start-up calls;
the HF clock switch uses ROM HAPI `HFSourceSafeSwitch`. Flash erase/program
also call the ROM (`ROM_API_FLASH_TABLE[5]`/`[6]`) with interrupts masked and
the cache disabled. The image first checks FCFG1 against the compiled chip
feature (wafer ID, flash size, +20 dBm PA) and halts on a mismatch.

Peripheral clocks are enabled in run **and** sleep mode: the Embassy executor
idles in `WFE`, and without the sleep gate UART0 stops mid-frame.

### LF clock: crystal with automatic RCOSC_LF fallback

The CCFG selects the 32.768 kHz crystal (XOSC_LF), as Z-Stack ships it. Some
ZBDongle-P V1.3 units never qualify their crystal: `DDI0_OSC STAT0` keeps
`SCLK_LF` on the RCOSC_HF-derived 31.25 kHz clock, and TI's Power driver
would wait for `LFSRCDONE` forever. `setup::start_lf_clock` therefore waits
at most `XOSC_LF_TIMEOUT_MS` (1 s, counted on the AON RTC from
`trim_device()`, where the boot ROM requested XOSC_LF). TI documents no
XOSC_LF start-up time; tuning-fork crystals within the datasheet's ESR and
load limits typically qualify within a few hundred ms. On timeout it does
what the ROM does for a CCFG RCOSC_LF (`OSCClockSourceSet(OSC_SRC_CLK_LF,
OSC_RCOSC_LF)`), waits for the switch and continues. One image serves every
dongle; the boot banner logs the source (`Crystal`, `RcOsc` or
`RcOscFallback`), the wait and, on RCOSC_LF, the measured offset. A crystal
that starts later is not switched back to.

What SCLK_LF drives and what RCOSC_LF changes:

- The AON RTC, i.e. the Embassy time base: every stack timer (commissioning
  and retry backoffs, Link Status and broadcast delivery times, route and
  child aging, indirect-frame expiry, the router's summary period). On
  RCOSC_LF the oscillator is measured once against XOSC_HF (4096 periods,
  DWT cycle counter) and the RTC increment is compensated, so time is
  accurate at the boot temperature; RCOSC_LF then drifts about 50 ppm/°C
  (datasheet) and is not recalibrated. These timers tolerate percent-level
  errors.
- Not the radio: MAC symbol timing, CSMA-CA backoffs, ACK wait and
  turnaround run on the RF core's RAT from XOSC_HF.
- Sleep: the router never enters standby. A sleepy image on RCOSC_LF would
  need periodic recalibration (TI `calibrateRCOSC_LF`) to keep poll and
  wake timing within the parent's child-aging limit.

The CCFG is unchanged (byte-identical to the previous images).

Hardware (ZBDongle-P V1.3 "#2", IEEE …C3:18:6D, ZHA 0xF107, flashed over
XDS110 cJTAG with the XOSC_LF CCFG): `STAT0.SCLK_LF_SRC` = RCOSC_LF after
the timeout; its RCOSC_LF measured +0.60 % (RTC increment `0x7F3B36`
instead of `0x800000`), so uncompensated timers would run 0.6 % fast. The
router resumed in the ZHA network; its Link Status period seen by the
nRF sniffer was 14.9999 s mean over seven intervals (15 s nominal; the
crystal dongle 14.9969 s in the same capture).

## Radio

`cc26x2_hal::rf` powers the RF core, copies TI's IEEE 802.15.4 CPE patch
(`vendor/ti/rf_patches`, BSD-3-Clause, generated into `rf/patch_ieee.rs` by
`tools/gen_rf_patch.py`), starts the RAT and runs `CMD_RADIO_SETUP` (PA
variant on P parts). Command layouts are pinned by host tests and
re-derived from the TI headers by `tools/check_rf_layout.c`.

| MAC function | RF core mechanism |
|---|---|
| receive | background `CMD_IEEE_RX`, 8-entry circular data queue, frame filtering |
| Imm-Ack | RF core auto-ACK for every frame that passes the filter (`hardware_auto_ack`) |
| Frame Pending | auto-pend for Data Requests from the source-match tables (16 short + 16 extended), armed by the parent `SoftMacCore` through `set_ack_frame_pending` |
| per-poll FP record | the RF core appends the source-match index to every stored frame (`rxConfig.bAppendSrcInd`, `0xFF` = no match); auto-pend sets the ACK's FP from that same match and every enabled entry is pending, so a Data Request without a match was ACKed with FP = 0 and reaches the MAC as `PhyRxFrame::acked_without_frame_pending` (the NWK keeps a frame queued since for the next poll) |
| transmit | `CMD_IEEE_CSMA` (PIB macMinBE/macMaxBE/macMaxCSMABackoffs) → `CMD_IEEE_TX` → `CMD_IEEE_RX_ACK` (54 symbols); the PHY repeats it for macMaxFrameRetries (`type Tx = FullTx`) |
| energy detect | `CMD_IEEE_ED_SCAN` |
| TX power | standard PA −20..+5 dBm; P parts: +20 dBm PA 14..20 dBm through the TX20 override list and `CMD_CHANGE_PA` (`RF_updatePaConfiguration`) |
| RF front-end switch | `rf::RfSwitch` (board-supplied lines): standard PA/receive drives the 2.4 GHz line high and the high-PA line low; the +20 dBm PA hands them to RFC_GPO0 (LNA enable) and RFC_GPO3 (PA enable), as TI's LaunchPad `rfDriverCallbackAntennaSwitching`. ZBDongle-P: DIO29 only |

The override words and PA tables are transcribed from the SDK radio-config
database (`setting_ieee_802_15_4.json`, `pasettings.json`); `rf/settings.rs`
cites each source. The P images default to +5 dBm: a 2 MHz-wide 802.15.4
signal above about +13 dBm conducted can exceed the ETSI EN 300 328
10 dBm/MHz density, so the product never selects the +20 dBm PA by default.

**AES.** NWK/APS CCM* runs on the CRYPTO engine (`cc26x2_hal::crypto`,
TI `AESECBCC26XX` sequence): the key is written through the engine's DMA
into key-store area 6 once per key change and loaded with `KEYREADAREA`,
each block is one ECB DMA transfer polled on `RESULT_AVAIL`; every wait is
bounded, a fault resets the engine and a DMA that stays busy poisons it.
The composition root installs it with `Cc26x2RadioPhy::install_aes_engine`
after two FIPS-197 known-answer tests; without it secured frames fail
closed. No software AES is linked: the router has no other AES user, and
the NCP takes the Trust Center Verify-Key and install-code hashes through
the MAC's provider (as on every platform, see
[Hardware Crypto](../advanced/hardware-crypto.md)); CI checks the
symbols. Host tests run the register sequence against a behavioural model
of the engine (FIPS-197 and the Zigbee CCM* golden vectors). Flash saved:
router −1,288 B (CC2652P 285,972 B), NCP −2,100 B (439,920 B).

On dongle #2 (ZBDongle-P V1.3, ZHA 0xF107) the hardware-AES router
resumed in the ZHA network: 113 NWK frames decrypted, 0 MIC failures in
its first two minutes, and every frame it sent that the nRF sniffer
captured verified with the network key (aux source = its own IEEE and
counter).

## Memory map (product-owned)

| | CC2652P (352 KiB) | CC2652P7 (704 KiB) |
|---|---|---|
| application | `0x00000..0x46000` (280 KiB) | `0x00000..0x9E000` (632 KiB) |
| GP Proxy Table journal | `0x46000..0x4A000` | `0x9E000..0xA2000` |
| child + APS journals | `0x4A000..0x52000` | `0xA2000..0xAA000` |
| security journal | `0x52000..0x56000` | `0xAA000..0xAE000` |
| CCFG sector | `0x56000..0x58000`, CCFG at `0x57FA8` | `0xAE000..0xB0000`, CCFG at `0xAFFA8` |
| SRAM | 80 KiB | 144 KiB |

Every image of a variant links the same map, Green Power or not, so a
reflash never moves persistence. `tools/verify-layout.py` checks every
image: flash bytes inside the application window, exactly one CCFG,
vector table, ≥ 12 KiB stack.

Each journal is the minimum two 8 KiB erase sectors (one sector is
rolled over while the other keeps the last snapshot), so the four router
journals take 64 KiB; none can shrink further without sharing an erase
sector. The GP Proxy Table (8 entries) is one 1 KiB record, so a sector
takes 8 full snapshots, or one plus 224 frame-counter records.

**CC2652P map change (GP window).** The ZBDongle-P map originally had no
GP window and a 296 KiB application. The 16 KiB GP window was taken from
the top of that application window; the child, APS and security journals
did not move, so a dongle joined with an earlier image keeps its network,
children and frame counters when updated (no re-pairing). The GP window
may still hold the tail of an earlier, larger image (images up to
287,252 B reached `0x46214`): the GP journal finds no valid record there,
starts with an empty Proxy Table and erases a sector before writing into
it (host test `foreign_bytes_in_both_sectors_are_erased_before_use`).
Flashing tools erase only the sectors an image covers; pass the new
application end (`cc26xx-rom-bsl.py --app-end 0x46000`) so that an
oversize image is refused and `--erase-persistence` includes the GP
window.

### Image sizes

The router is built with `opt-level = "z"`, `-Zlocation-detail=none` and
debug/trace log sites compiled out (`log/max_level_info`). The release log
level is a feature, exactly one of `info-log` (default) and `quiet-log`
(warnings and errors only).

Green Power Proxy Basic (`green-power`) adds ≈ 27 KB of code (GPDF
receive and tunnelling, the GP Proxy Table journal, `zigbee-gp`) and
2.3 KiB of static RAM. On the CC2652P it fits only with `quiet-log`
(≈ 22.8 KB of info-level log sites) and the `release-compact` profile
(`.cargo/config.toml`: `release` with the nightly `immediate-abort` panic
strategy, ≈ 11 KB): every panic site becomes one `udf` trap, so the
`HardFault` handler logs the faulting PC (the panic site, resolvable with
the ELF) and halts, as the panic handler would, but without the message.

```sh
cd examples/cc26x2-router
cargo build --release                                             # CC2652P
cargo build --profile release-compact --no-default-features \
  --features zbdongle-p,green-power,quiet-log                     # CC2652P + GP
cargo build --release --no-default-features \
  --features cc2652p7-dongle,info-log[,green-power]               # CC2652P7
```

| image | flash | of window | static RAM | stack |
|---|---:|---:|---:|---:|
| CC2652P router | 286,020 B | 99.8 % (700 B free) | 35,304 B | 46,616 B |
| CC2652P router + GP (`quiet-log`, `release-compact`) | 278,348 B | 97.1 % (8,372 B free) | 37,652 B | 44,268 B |
| CC2652P7 router | 286,120 B | 44.2 % | 35,304 B | 112,152 B |
| CC2652P7 router + GP | 312,448 B | 48.3 % | 37,652 B | 109,804 B |

Measured on a local macOS build with the per-poll FP = 0 record and the RX
entries in `.bss`; CI's Linux build of the plain CC2652P router came out
96 B smaller before that change (32 B free in CI, a 64 B overflow locally).
The plain CC2652P router keeps info logs and panic messages; with this
little left in its window, further growth must come with a size cut (for
example the same `quiet-log` / `release-compact` choices).

**Green Power status.** Host-tested (runtime GP proxy and journal tests,
product with `green-power`); both GP images pass the layout and symbol
gates. On dongle #2 (ZBDongle-P V1.3, ZHA 0xF107) the CC2652P GP image
(0f11351, app-only flash over the hardware-AES router, journals kept)
booted and resumed as 0xF107 without rejoining: ZHA saw it again within
two minutes and the sniffer captured it routing and originating NWK
traffic. Its GP window still held the 0x220-byte tail of an earlier
image, as expected (no pairing yet, so nothing was written). GPD
forwarding through this proxy is **not yet verified on hardware**: it
needs a GP Proxy Commissioning Mode or a GP Pairing from the sink, i.e.
a ZHA permit-join window with a GPD commissioning.

## ZRHP network co-processor (CC2652P7)

`examples/cc26x2-ncp` composes the shared `apps/ncp-coordinator` (ZRHP v1,
[host protocol](../advanced/host-protocol.md)) with a CC26x2 platform
layer; `products/cc26x2-ncp` owns the identity (`CC2652P7-NCP`, ZRHP chip
code 11), the NV layout, the journals' opening policy and the UART
transport. The coordinator is the same Trust Center + Green Power combo
(Proxy Basic + Sink, without the TempMaster: the CC26x2 MAC has no timed
transmission yet) as the ESP32-H2 NCP, on `Cc26x2RouterMac` with
`pan-coordinator`.

**Transport.** UART0 through the dongle's USB-UART bridge, 8N1, default
460 800 baud, no RTS/CTS (`SYS_SET_UART`: 115 200 / 460 800 / 921 600;
flow control is refused). Receive is interrupt-driven into an 8 KiB ring
(≥ 8-frame window × 656 B, spec 4.1), transmit is an interrupt-fed 2 KiB
ring (`cc26x2-hal` `uart-host-rings`). Framing/parity/break errors and
overruns are reported as line faults. Flash erase/program masks interrupts
for milliseconds, so bytes beyond the 32-byte FIFO can be lost then; ARQ
recovers the frame. A μDMA receive path would remove that window.

**Capacity: `compact`.** The ESP32-H2 capacities (`ncp-capacity`: 256 Trust
Center devices and link keys, 512 address map, 96 neighbors, 16-frame link
window) need about 164 KiB of static RAM on the Cortex-M4 — more than the
CC2652P7's 144 KiB. The image enables `ncp-coordinator-app/compact`
(`zigbee-runtime/ncp-capacity-compact`):

| Table | `ncp-capacity` (ESP32-H2) | `compact` (CC2652P7) |
|---|---:|---:|
| Trust Center devices / APS link keys | 256 / 256 | 128 / 128 |
| Address map | 512 | 256 |
| Neighbors / NIB `max_children` | 96 / 64 | 64 / 32 |
| Source routes | 128 | 64 |
| NWK replay floors | 128 | 96 |
| Indirect queue, persisted children, GP Sink Table | 16, 64, 16 | unchanged |
| ZRHP link window (each way) / endpoint queue | 16 / 1 536 B | 8 / 1 024 B |

The window is negotiated (spec minimum 4); journal formats are the
`ncp-capacity` ones (Trust Center record version 7, which reads version 6;
1 KiB child slots). Images without
the feature are unchanged.

**Memory map** (`products/cc26x2-ncp/link/memory-cc2652p7.x`, checked by
`verify-layout.py --layout ncp`):

| Window | Range | Geometry |
|---|---|---|
| application | `0x00000..0x86000` (536 KiB) | — |
| identity/settings (reserved) | `0x86000..0x8A000` | 2 × 8 KiB |
| APS tables | `0x8A000..0x8E000` | 2 × 8 KiB |
| Green Power | `0x8E000..0x92000` | 2 × 8 KiB |
| children | `0x92000..0x96000` | 2 × 8 KiB |
| Trust Center stream | `0x96000..0xA6000` | 2 × 32 KiB |
| security | `0xA6000..0xAE000` | 2 × 16 KiB |
| CCFG sector | `0xAE000..0xB0000` | — |

Opening policy: no valid security record (blank flash, Z-Stack NV) erases
all NCP windows; a valid record of another role (`select_role_tag`) keeps
the outgoing counter limits, clears the keys and erases that role's other
journals; a valid NCP journal is kept.

**Size** (release, `opt-level = "z"`): flash 422,488 B of 548,864
(77.0 %), static RAM 116,748 B, 30,708 B left for the stack.

**Firmware update.** Only through the serial ROM bootloader (CCFG backdoor
kept enabled, compile-time gate): the host enters it with the bridge's
DTR/RTS lines and programs the application sectors only (hwlab `tibsl`
or `tools/cc26xx-rom-bsl.py`), never the NV windows. `FW_*` is not built
in and `SYS_RESET` mode 1 only reboots. A/B slots are not possible even
on the CC2652P7: two 422 KB images plus 160 KiB of NV exceed 704 KiB.

**CC2652P: not feasible.** The NCP code alone (≈ 422 KB) exceeds the
CC2652P's 344 KiB below the CCFG sector before any NV journal, and its
static RAM (≈ 117 KiB in the compact tier) exceeds the 80 KiB SRAM. Even
without Green Power (≈ 45 KB of code) it does not fit. The ZBDongle-P stays
a router; a ZRHP NCP needs a CC2652P7 (or larger) part. The product crate
refuses the `zbdongle-p` feature with a compile error.

**Validation.** Builds, layout/CCFG gate, host tests (product layout, UART
policy; `ncp-coordinator-app` with `compact`). Not run on hardware: no
CC2652P7 unit is available in the lab.

## CCFG and recovery

On a USB dongle the serial ROM bootloader is the only way back in. The board
crate builds the CCFG (`Ccfg::ti_default().lf_clock(Crystal).rom_bootloader(DIO15, active low)`,
byte-identical to the shipped ZBDongle-P CCFG), the product links it into
`.ccfg`, and `Ccfg::check_recoverable()` is a compile-time gate: an image
that disables the bootloader, protects sectors or turns the cache off does
not build. `cc26x2_hal::flash::Flash` refuses to erase or program the CCFG
sector at run time.

## Lab images pinned to one channel

`CC26X2_ROUTER_CHANNEL=<11..26>` at build time restricts network steering to
that channel (the image logs a TEST-ONLY warning). Use it for unattended
bench runs on an empty channel, and for a join test on the lab
coordinator's channel so the router cannot join another open network.

`CC26X2_ROUTER_ACK_PROBE=1` (TEST-ONLY, logged) sends one unicast
IEEE_addr_req to the coordinator per summary period, so the summary's
`ar-unicast` (delivered unicast frames that requested an ACK) can be
compared with the RF core's `auto-acks`. The RF core output counters
(`auto-acks`, `buf-full`, `nok`) are 8-bit and wrap.

`CC26X2_LOG_RAM=1` (TEST-ONLY) also writes the log into an 8 KiB RAM ring
(`CC26X2_LOG_RAM`, write index `CC26X2_LOG_RAM_HEAD`, addresses from
`nm`) that a debug probe reads while the router runs — for a dongle whose
UART is not connected (dongle #2 on the XDS110).

## Flashing (ROM bootloader over UART)

The ZBDongle-P CP2102 drives RESET and the DIO15 backdoor: `DTR=0,RTS=1`
holds RESET, `DTR=1,RTS=0` pulls DIO15 low (pyserial levels, measured). Both
lines must change in one `TIOCMSET`; `cc2538-bsl --bootloader-sonoff-usb`
does not enter the bootloader on the lab unit.

The lab flashes with hwlab's `tibsl` plugin (device id from the USB port
location, e.g. `cp210x-loc20-7.2`, or the cached IEEE). Program a raw image
**without** the `.ccfg` section — a flat binary that reaches the CCFG would
fill the persistence partitions in between:

```bash
ELF=examples/cc26x2-router/target/thumbv7em-none-eabihf/release/cc26x2-router
rust-objcopy -O binary --remove-section .ccfg $ELF router.bin
hwlab target flash backup  --plugin tibsl --device cp210x-loc20-7.2 --yes
hwlab target flash program --plugin tibsl --device cp210x-loc20-7.2 --path router.bin \
  --token program-flash --arg backup=<fresh backup .bin> --arg reset_after=true --yes
```

hwlab erases and rewrites only the sectors the image covers and changes,
verifies with the ROM CRC32, and touches the CCFG sector only with
`--token-config modify-ccfg`. `tools/cc26xx-rom-bsl.py` is the standalone
equivalent (application sectors only, persistence only with
`--erase-persistence`, CCFG last and only when it changes, refuses a CCFG
that would disable the bootloader).

## Hardware evidence (Sonoff ZBDongle-P, CC2652P1F PG3, EUI-64 00:12:4B:00:20:CD:1D:7D)

- Identification and backup: ROM bootloader, two full-flash reads with equal
  SHA-256 and matching ROM CRC32 (`~/.hwlab/artifacts/cc2652p-00124b0020cd1d7d-backup`).
- `cc26x2-lab`: trim, chip check, XOSC_HF, 32.768 kHz crystal, 1000 ms timer
  measured as 1000 ms, TRNG, flash erase/program/verify on the top
  application sector, CCFG-sector erase refused, RF core power-up/patch/setup,
  ED on 11..26, active scan (16 Beacon Requests sent, 0 busy, 0 errors) with
  beacons from five networks including the lab ZHA network (PAN 0xDFE9,
  channel 15, seven routers), 468 frames received promiscuously in 20 s.
- `cc26x2-router` (TEST-ONLY `CC26X2_ROUTER_CHANNEL=26` build, channel 26 only): boots,
  erases foreign persistence, runs BDB network steering with bounded retries.
- `cc26x2-router` (all channels) joined the lab ZHA network (PAN 0xDFE9,
  channel 15, NWK 0x6D6B, parent 0xD586) while its permit join was open;
  ZHA interviewed it as "Zigbee-RS CC2652P-Router" (Router, available).
  After every reflash/reset it resumes from the journals (no rejoin),
  restores 10 neighbours, relays broadcasts and answers NWK_addr_req.
- Unicast RX auto-ACK (TEST-ONLY `CC26X2_ROUTER_ACK_PROBE=1`: a unicast
  IEEE_addr_req to the coordinator each minute): the coordinator's answer
  arrived; `ar-unicast` (delivered unicast frames with AR = 1) equals the
  RF core's `nTxAck` (`auto-acks`); our unicast TX: 0 no-ACK.
- FCS failures: the RF core reports about 15 % of the frames that pass the
  address filter as CRC errors (`nok`) on channel 15. The lab sniff gate
  keeps CRC-error frames (`Radio::set_keep_crc_errors`): they sit at
  −80..−71 dBm with lower correlation (≈ 40 vs ≈ 51), no frame at all is
  heard below −80 dBm, and ED reads −78..−87 dBm on quiet channels — an
  elevated noise floor at the lab position (USB hub) rather than a settings
  error (override words and PA tables are pinned against the SDK by host
  tests). Driving the previously floating RF-switch line (DIO29) low did
  not change the rate. An independent sniffer comparison is still open.
- Broadcast Transaction Table: a burst of more than 16 broadcasts within
  9 s from one Green Power proxy (0x6EDC) filled the 16-entry BTT; the
  router dropped (did not relay) the excess as R22 §3.6.5 requires. This is
  the shared `zigbee-nwk` size (`MAX_BTR`), not CC26x2-specific.

The per-poll FP = 0 record (`RxInfo::source_matched`, see
[Frame Pending: choose one owner](../advanced/soft-mac-porting.md#frame-pending-choose-one-owner))
is host-tested (entry decoding with the appended index, the stale-poll
sequence) and build-checked only. The RX data entries grew by that byte
(136 → 140 B each) and moved out of the `.data` image of `RF_MEM` into
`.bss` (`RX_DATA_ENTRIES`): their zeros no longer occupy flash, which keeps
the ZBDongle-P router inside its 280 KiB window (32 B were left before).

Open: a child joining through it (Frame Pending, the per-poll FP = 0
record), ACK timing against an
independent sniffer, sniffer comparison of the CRC-error rate,
OTA, long-duration stability, the +20 dBm PA path, CC2652P7 hardware.
