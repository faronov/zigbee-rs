# TI CC2340R5

The LP-EM-CC2340R5 sensor is a pure-Rust Cortex-M0+ application around TI's
documented radio command interface. It imports the pinned SDK's IEEE radio
microcode/settings as data; it does not link RCL, ZBOSS, FreeRTOS, or a C
platform runtime.

## Layering

```text
environmental Sleepy End Device profile
        ↓
products/cc2340-sensor
        ↓
boards/lp-em-cc2340r5
        ↓
CC2340 register/radio mechanisms + MacDriver
```

`examples/cc2340-sensor` is the short composition root.

The board owns:

- real 48 MHz/SysTick time;
- LED1 DIO7 and LED2 DIO6;
- Button 1 DIO13 and Button 2 DIO14;
- IOC/GPIO setup;
- typed physical LED/button resources;
- reset, factory identity, and physical flash.

The product owns the environmental profile, synthetic/fixed measurements,
`Active`/`Active` wait policy, identity strings, protected security partition,
and linker layout.

The composition root maps the raw physical resources to sensor status and user
action behavior, installs RTT diagnostics, and selects reset supervision.
The board crate contains none of those application semantics.

## Application composition

```rust,ignore
SensorSedParts {
    wake,

    environment: SyntheticEnvironment::new(),
    battery: fixed_battery(),
    ota: NoOta,
    actions: USER_ACTIONS,

    diagnostics,
}
```

The image uses software AES. Commissioning still fails closed because no
production entropy source has been qualified. Returning a fake entropy value
would make Zigbee keys predictable, so the application does not do that.

## Storage

```text
0x00000000..0x0007E000  application
0x0007E000..0x00080000  SecurityStateJournal
```

The product bounds the board flash resource and constructs the journal. Flash
controller behavior remains a hardware gate.

The main task uses Embassy's compiler-sized static storage with the pinned
nightly, rather than its insufficient default 4 KiB arena. That storage is
accounted for in `.bss` before the image can link. Both copies of the product
linker layout require at least 16 KiB of stack reserve in the actual 36 KiB
SRAM region; increasing task state can no longer silently consume that reserve.
This does not qualify the radio or replace a runtime stack high-water test.

## Build

General target code uses `nightly-2026-03-23`. The release radio image requires
the exact SDK source pinned by CI:

```bash
git clone https://github.com/TexasInstruments/simplelink-lowpower-f3-sdk.git
git -C simplelink-lowpower-f3-sdk checkout \
  68ca021502383f367d0bf2a5517fdd0dcb0ef909

cd examples/cc2340-sensor
CC2340_SDK_DIR=/absolute/path/to/simplelink-lowpower-f3-sdk \
  cargo +nightly-2026-03-23 build --release --locked --target-dir target/sdk
```

With `CC2340_SDK_DIR` unset, the fallback image must compile but radio
initialization returns `FirmwareUnavailable`. This tests fail-closed behavior;
it is not a usable radio image.

The exact fallback command is:

```bash
env -u CC2340_SDK_DIR \
  cargo +nightly-2026-03-23 build --release --locked \
  --target-dir target/fallback
```

The pre-static-task pinned-SDK image measured 223,536 B against a 225,280 B
regression gate. Its former 4,772 B static-RAM figure included the undersized
arena and was not a valid task-capacity check. The 2026-09-10 fallback build
instead contains a 16,776 B static main-task pool, occupies 17,444 B of SRAM,
and leaves 19,420 B below the initial stack pointer. Its raw application is
213,160 B. It is still the explicit
`FirmwareUnavailable` build, not a refreshed pinned-SDK radio qualification.
The physical application slot remains 516,096 B (`0x7E000`).

## Hardware status

Build and static-layout validation pass. No CC2340 board has completed the
radio bring-up gates. Still open:

- raw TX/RX and FCS;
- scan/beacon parsing;
- association and ACK timing;
- entropy backend;
- secured commissioning and interview;
- journal program/erase and reset recovery;
- power behavior.

Do not describe the CC2340 product as commissionable until both radio HIL and
entropy are complete.
