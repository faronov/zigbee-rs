# TI CC2340R5

The LP-EM-CC2340R5 sensor is a pure-Rust Cortex-M0+ application around TI's
documented radio command interface. It imports the pinned SDK's IEEE radio
microcode/settings as data; it does not link RCL, ZBOSS, FreeRTOS, or a C
platform runtime.

## Layering

```text
environmental Sleepy End Device profile
        ↓
products/cc2340-sensor
        ↓
boards/lp-em-cc2340r5
        ↓
cc2340r5-hal (chip services + peripheral drivers)
        ↓
CC2340 register/radio mechanisms + zigbee-mac Cc2340RadioPhy on SoftMacCore (Cc2340SoftMac)
```

`examples/cc2340-sensor` is the short composition root.

`cc2340r5-hal` owns the chip services shared by every CC2340R5 board:

- the LF RCOSC clock, VDDR regulator and standby;
- the SYSTIM Embassy time driver;
- generic IOC/GPIO `Led<DIO>` and `Button<DIO>` types;
- BATMON, factory identity, reset and the internal flash controller;
- reusable peripheral drivers: an `embedded-hal` I2C controller, the 12-bit
  ADC and LGPT PWM;
- the `LAES` AES-128 engine (`cc2340r5_hal::aes`, see
  [Hardware crypto](#hardware-crypto)).

Peripheral drivers stay clock-gated until a board or product uses them.
Board crates, in-tree or out-of-tree, take these services through
`take_core()` and add only their pin map. The I2C, ADC and PWM register
sequences are host-tested against fakes but have not run on silicon.

The LaunchPad board owns:

- LED1 DIO7 and LED2 DIO6;
- Button 1 DIO13 and Button 2 DIO14;
- the typed physical LED/button resources it builds from the HAL.

The product owns the environmental profile, the BATMON-backed measurements
(die temperature, VDDS supply) plus a synthetic humidity drift, the
`Idle`/`Retention` wait policy (250 ms fast poll, 10 s slow poll), identity
strings, protected security partition, and linker layout.

The composition root maps the raw physical resources to sensor status and user
action behavior, installs RTT diagnostics, and selects reset supervision.
The board crate contains none of those application semantics.

## Application composition

```rust,ignore
SensorSedParts {
    wake,
    status,
    environment: product::environment::BatmonEnvironment::new(batmon),
    battery: product::battery::BatmonBattery::new(batmon),
    ota: NoOta,
    actions: product::policy::USER_ACTIONS,
    supervisor,
    diagnostics,
}
```

The temperature cluster reports the BATMON die temperature, not ambient
temperature; humidity is a synthetic 35–65 %RH drift until a sensor is fitted.

Zigbee AES runs on the `LAES` hardware engine (see
[Hardware crypto](#hardware-crypto)); no software AES is linked.
`Cc2340RadioPhy::fill_random` is served by an AES-128 CTR_DRBG seeded from
radio ADC noise before the radio starts (see [Entropy](#entropy)). If the
noise capture, a health test or the DRBG known-answer test fails, the image
keeps running and every request fails closed (`MacError::Unsupported`); it
never substitutes predictable bytes.

`Idle` waits power the radio down and sleep on the SYSTIM alarm (WFE); slow
polls with `Retention` enter TI standby on the internal 32 kHz oscillator and
re-initialize the radio cores afterwards, keeping the loaded LRFD images.

## Hardware crypto

The CC2340R52 `LAES` core (`AES_BASE` 0x400C_0000, clock gate
`CLKCTL.CLKCFG0.LAES`) is the only AES-128 implementation in every CC2340
image (sleepy sensor, always-on End Device, fallback image).

- **Engine:** `cc2340r5_hal::aes::AesEngine`, built from the singleton
  `aes::Aes` token in `Core` (passed through `lp_em_cc2340r5::Resources`).
  One forward block per call: `ICLR`, `KEY0..3`,
  `AUTOCFG = AESSRC_BUF | TRGAES_WRBUF3S`, `BUF0..3` (the `BUF3` write
  starts the operation), bounded poll for `RIS.AESDONE` with `STA` idle,
  `TXT0..3`, then `ABORT` + `ICLR`. Register words carry the standard byte
  stream little-endian, exactly as `AESCopyBlock` writes it. This is the
  CPU single-block path of TI's `AESECBLPF3.c` / `AESCommonLPF3.c` and
  `driverlib/aes.h` (SimpleLink Low Power F3 SDK, `hw_aes.h`), except that
  `AUTOCFG.BUSHALT` stays off so a wedged core becomes a bounded
  `Timeout` instead of a bus stall. Errors (`ZeroIterations`,
  `ClockUnavailable`, `Busy`, `Timeout`, `KnownAnswerMismatch`) publish no
  output; `ABORT` leaves no plaintext or ciphertext in `TXT`/`BUF`.
- **MAC backend:** `Cc2340RadioPhy::install_aes_engine(aes)` consumes the
  token, enables the clock and runs a two-key FIPS-197 self-test on silicon.
  `ForwardAesProvider::forward_cipher` returns `Cc2340HardwareAes128`; it
  fails with `Cc2340AesError::NotInstalled` until an engine is installed and
  never falls back to software. The `zigbee-mac` `cc2340` feature always
  enables `hardware-aes-cc2340`.
- **Composition root:** `main.rs` and `roles.rs` install the engine right
  after constructing the PHY and halt (Zigbee never starts) if the self-test
  fails; RTT prints `LAES AES-128 self-test passed`.
- **Ownership:** the radio (LRFD/PBE in `zigbee-mac`, and TI's RCL) never
  uses `LAES`; TI's own Zigbee stack runs its security on the CPU through the
  same `AESECB` driver. The uDMA channels TI can route to `LAES` are unused.
  The loader (`take_boot`) never receives the token.
- **Standby:** the clock stays on for the engine's lifetime, like TI's open
  AES handle. Peripheral registers are assumed lost in standby (TI's I2C,
  UART2, SPI, LGPT and uDMA drivers re-initialise on
  `PowerLPF3_AWAKE_STANDBY`; its AES drivers keep no state between
  operations and need no hook). Every block reprograms `KEY`, `AUTOCFG` and
  `BUF` and ends with `ABORT`; standby never interrupts a block. If the
  `LAES` clock is ever found gated, it is re-enabled and the self-test runs
  again before any output is used.
- **CI:** the CC2340 job rejects `aes::soft`/`SoftwareAes128` in the fallback,
  sensor and End Device ELFs and requires `Cc2340HardwareAes128` plus the
  `LAES` self-test.

Validation level: **lab-tested on hardware** (LP-EM-CC2340R5, CC2340R52,
2026-11-22, SDK image `cc2340-sensor`, XDS110 SWD). The host register model
passes every `zigbee_crypto::kat::run_all` vector (FIPS-197/SP 800-38A
blocks, IEEE 802.15.4 Annex C CCM*, Zigbee CCM* M=4, install-code AES-MMO)
plus fail-closed tests for a zero poll budget, gated clock, busy core,
timeout (abort, no partial output), stale `AESDONE` and wrong silicon output.
On silicon:

- RTT `LAES AES-128 self-test passed` on every boot; with `BUSHALT` off the
  `RIS.AESDONE` poll completes and the result reads back correctly;
- factory-new join to ZHA (channel 15, PAN 0xDFE9) as 0x22BE, interview
  (`Zigbee-RS` / `CC2340-Sensor`), temperature/humidity/battery reports; the
  committed security journal holds a link key other than ZigBeeAlliance09,
  i.e. the unique-TCLK exchange completed (the RTT ring overflowed before
  the Request-Key/Verify-Key lines, so they were not captured);
- system reset → `Resume: addr=0x22BE PAN=0xDFE9 ch=15 parent=0xF020`, no
  new association, reports continue.

Not run on silicon: the engine `Timeout` path (a wedged core) and engine
behaviour after real standby.

## Entropy

The CC23x0 has no general-purpose TRNG. TI's `RNGLPF3RF` driver
(`ti/drivers/rng/RNGLPF3RF.c`) collects IF-ADC noise while the radio is
otherwise unused (`RCL_AdcNoise_get_samples_blocking()`), health-tests it,
compresses it with AES-CBC-MAC into a 256-bit seed and serves requests from
an AES CTR_DRBG. `zigbee-mac/src/cc2340/{noise,entropy}.rs` do the same in
Rust; no TI library is linked.

```text
seed_entropy()  (boot, before initialize_radio)
  noise.rs    LRF_configAdcNoise + RCL_Handler_ADC_Noise_getNoise, direct registers
              -> 1024 S2R words in PBE RAM (3072 I + 3072 Q 5-bit codes)
  entropy.rs  repetition count / adaptive proportion / top-two proportion / format
              -> CBC-MAC-AES-128 (fixed key) over each 2 KiB half -> 256-bit seed
  zigbee-crypto::ctr_drbg  AES-128 CTR_DRBG, no df (SP 800-90A 10.2.1),
              personalization = label || EUI-64, KAT before every seed
fill_random()  -> CTR_DRBG generate on the LAES engine
```

- **Noise acquisition** (`noise.rs`): what RCL does for `RCL_CMD_ADC_NOISE_GET`
  under `LRF_configAdcNoise` (`adc_noise_bt5_cc23xx.json`): HFXT and its
  radio buffer, the LRFD clocks, the BLE5 **RFE** image only (PBE/MCE
  disabled), the 142 ADC-noise register fields, `RSSI` invalid,
  `FIFOCMDADD`, FCFG trims with `bwIndex = bwIndexDither = 1`, synth refsys;
  then `RCL_Handler_Adc_Noise_powerUp()` (2440 MHz `K5`/`CALMMID_CALMCRS`/
  `PLLM0`/`PLLM1`, RFE TOPsm boot, `LRFDRFE.MSGBOX == 4`, RFE command 4 =
  PLL calibration via `LRFDPBE.RFEAPI`), `configureS2R()`
  (`LRFDDBELL.CLKCTL.S2R`, `LRFDMDM.ADCDIGCONF = I|Q`, `LRFDS2R.CFG =
  ONESHOT|SEL_ADCDIG|CTL_EN`, `START/STOP` = PBE RAM), on `RIS0.RFEDONE` RFE
  command 3 (RX start; wait `LRFDMDM.RFECMDIN` bit 3), LNA and mixer
  dividers off (`LRFDRFE.LNA.EN`, `DIVCTL.RXPH90DIV/RXPH0DIV`), `ADCDIG`
  reset/enable, `LRFDS2R.TRIG = ARM`, wait for `LRFDS2R.STAT.RUNNING` to
  clear, then `powerDown()` (RFE commands 1 and 5 acknowledged through
  `LRFDPBE.RFEMSGBOX`, S2R/ADCDIG/RFE off). The samples are consumed in
  place and wiped; LRFD clocks and HFXT are stopped again. Every wait is
  bounded by the SYSTIM (TI's handler spins without bound) and PLL
  completion is polled in `RIS0` instead of taking the LRFD interrupt.
  `build.rs` imports the register fields and stores the BLE5 RFE image as
  three patch runs (321 words) over the IEEE RFE image the radio needs
  anyway; the build asserts the rebuilt image equals the SDK array and a
  host test checks its checksum. Both imported register tables (IEEE: 256
  fields in 110 writes, ADC noise: 142 fields in 60 writes) are packed into
  4-byte `(address code, value)` pairs (`address = 0x4008_0000 + 2 * code`,
  16-bit writes for the TOPsm RAM blocks at `0x4009_0000` and above, 32-bit
  writes below); `build.rs` refuses a table that breaks the rule and host
  tests compare every decoded write with the resolved table. A fallback
  build (no SDK) has no noise configuration and drops the whole seed path.
- **Health tests** (startup and on every reseed capture, each code of both
  streams): SP 800-90B repetition count (`C = 41`), adaptive proportion over
  512-code windows for every code value (`C = 410`), a developer-defined
  top-two proportion test against a collapse onto two codes (`C = 430`), and
  a word-format check (bits 15/31 must be zero). The cutoffs assume
  `H = 0.5` bit/code at `alpha = 2^-20`. TI's own `APT bimodal` rule (two
  4-bit bins each above 369 in a 516-code window) can never trigger; the
  top-two test replaces it.
- **Conditioning**: CBC-MAC-AES-128 under a fixed, non-secret key over each
  512-word half, as TI does (SP 800-90B vetted conditioning). Each 128-bit
  output absorbs 3072 codes, i.e. 1536 bits at the assumed `H`.
- **DRBG**: AES-128 CTR_DRBG without derivation function (full-entropy
  seed), personalization string = `zigbee-rs CC2340R5 DRBG ` || EUI-64.
  Before every (re)seed the NIST CAVP `[AES-128 no df]` no-reseed vector
  `COUNT 0` runs on the `LAES` engine. Working state is wiped on drop and
  on any engine error.
- **Reseed / prediction resistance**: seeded at every boot; a reseed is
  due after 2^20 requests (SP 800-90A allows 2^48) and is performed by the
  next `fill_random` made while the radio is not initialised or asleep
  (the capture overwrites the PBE/RFE images, so the driver then reloads
  them on wake); until then requests fail closed. Prediction resistance is
  not offered: a capture stops the IEEE radio.
- **Ownership**: the PHY owns both the `LAES` engine and the DRBG state;
  conditioning, the DRBG and CCM* borrow the engine through one
  `ForwardAesProvider` (`LaesProvider`), never concurrently. The noise
  capture owns the whole LRFD and is refused (`EntropyError::RadioBusy`)
  while the IEEE radio is running or holds an undelivered frame.
- **Fail closed**: `EntropyDisposition` is `Unseeded`,
  `RadioNoiseCtrDrbg` or `FailedClosed(error)`. Unseeded or failed:
  `fill_random` returns `MacError::Unsupported` and leaves the buffer
  untouched; an engine error during a request returns `SecurityError`,
  zeroises the buffer and fails the source closed. A new `seed_entropy()`
  repeats the startup tests. The images log a failure as
  `entropy failed closed (code 0xNN)` (`EntropyError::code`, no `Debug`
  formatting in the image): `0x01`..`0x06` `Unseeded`, `AesUnavailable`,
  `RadioBusy`, `Cipher`, `KnownAnswerMismatch`, `ReseedRequired`;
  `0x10 + n` `Noise(NoiseError)` in declaration order (`Unavailable` = 0 ..
  `StopTimeout` = 10); `0x20` word format; `0x22`/`0x23` repetition count
  (I/Q); `0x24`/`0x25` adaptive proportion (I/Q); `0x26`/`0x27` top-two
  proportion (I/Q).
- **Lab image**: `cargo build --release --features entropy-lab --bin
  cc2340-entropy-lab` (feature `zigbee-mac/cc2340-entropy-lab`, the only way
  to read raw noise; no product enables it) characterises the source and
  the DRBG output and leaves the results in the `LAB` symbol.

Measured on the LP-EM-CC2340R5 (CC2340R52, 2026-11-22, lab image, three
runs): 256 captures each without a health-test or capture failure; 20–21
of 32 code values occur; most-common-value estimate 1.74 (I) / 1.71 (Q)
bit/code; lag-1/2/3 predictor estimates 1.05/1.50/1.54 (I) and
1.15/1.41/1.50 (Q) bit/code; longest run 20 codes, largest one-code window
count 199/512, largest top-two count 261/512. These are characterisation
numbers, not an SP 800-90B assessment. `seed_entropy` takes 24.5 ms
(HFXT start, capture, 272 `LAES` blocks), 4 KiB of DRBG output 8.1 ms.
64 KiB of DRBG output per run: monobit z = 0.22 / 0.87 / 2.53, byte
chi-square 252 / 218 / 263 (255 degrees of freedom), runs z = −0.39 / 1.18
/ 0.47; first output blocks differ on every boot. This is a sanity check,
not a certification.

Validation level: **lab-tested on hardware** (one board). The sensor image
logs `entropy seeded: CTR_DRBG KAT and noise health tests passed` on every
boot, then brings the IEEE radio up from the reloaded images, resumes on the
network, and completes a fresh join (Transport-Key, Request-Key, unique
TCLK, Verify-Key, Confirm-Key SUCCESS). The size-reduced image (packed
register tables, shared DRBG counter loop, error codes; 248,384 B) was
re-flashed over the commissioned state: the same boot lines, the IEEE radio
up from the packed PHY table, resume as `0xAB91`, secured reports
acknowledged and shown in ZHA. Not run on silicon: a reseed triggered by
the request counter (2^20 requests), a capture after real standby, and any
failure path (they are host-tested).

## Storage

```text
0x00000000..0x0007E000  application
0x0007E000..0x00080000  SecurityStateJournal
```

The product bounds the board flash resource and constructs the journal. Flash
controller behavior remains a hardware gate.

The main task uses Embassy's compiler-sized static storage with the pinned
nightly, rather than its insufficient default 4 KiB arena. That storage is
accounted for in `.bss` before the image can link. Both copies of the product
linker layout require at least 16 KiB of stack reserve in the actual 36 KiB
SRAM region; increasing task state can no longer silently consume that reserve.
This does not qualify the radio or replace a runtime stack high-water test.

## Build

General target code uses `nightly-2026-03-23`. The release radio image requires
the exact SDK source pinned by CI:

```bash
git clone https://github.com/TexasInstruments/simplelink-lowpower-f3-sdk.git
git -C simplelink-lowpower-f3-sdk checkout \
  68ca021502383f367d0bf2a5517fdd0dcb0ef909

cd examples/cc2340-sensor
CC2340_SDK_DIR=/absolute/path/to/simplelink-lowpower-f3-sdk \
  cargo +nightly-2026-03-23 build --release --locked --target-dir target/sdk
```

With `CC2340_SDK_DIR` unset, the fallback image must compile but radio
initialization returns `FirmwareUnavailable`. This tests fail-closed behavior;
it is not a usable radio image.

The exact fallback command is:

```bash
env -u CC2340_SDK_DIR \
  cargo +nightly-2026-03-23 build --release --locked \
  --target-dir target/fallback
```

The pre-static-task pinned-SDK image measured 223,536 B against the former
225,280 B regression budget, which is no longer enforced. Its former 4,772 B
static-RAM figure included the undersized arena and was not a valid
task-capacity check. The 2026-09-10 fallback build
instead contains a 16,776 B static main-task pool, occupies 17,444 B of SRAM,
and leaves 19,420 B below the initial stack pointer. Its raw application is
213,160 B. It is still the explicit
`FirmwareUnavailable` build, not a refreshed pinned-SDK radio qualification.
The physical application slot remains 516,096 B (`0x7E000`); memory, partition,
and stack checks remain mandatory.

## Bootloader and OTA staging

Products that need over-the-air updates can keep an MCUboot-compatible
layout (for example a 16 KiB loader at `0x0`, primary and secondary slots,
and an NV region) with two reusable pieces:

- `mcuboot-image` (workspace crate, `no_std`): imgtool header/TLV parsing,
  SHA-256 + ECDSA P-256 validation, MCUboot trailer magic, the
  overwrite-only install decision with MCUboot's downgrade rule, a
  `LoaderInfo` record, and (feature `firmware-writer`) a
  `zigbee-runtime` `FirmwareWriter` that stages an image in the secondary
  slot and writes the trailer magic only on activation;
- `bootloaders/core` (`zrs-boot-core`, workspace crate): the shared boot
  sequence, entry checks, status indication and the power-cut flash
  simulator (see [Bootloader Core](../advanced/bootloader.md));
- `bootloaders/cc2340r5-boot` (standalone): the CC2340R5 shell of that
  core. It uses the
  HAL boot profile (`default-features = false`, `take_boot()`), installs a
  pending image, validates the primary, checks the vector table, sets
  `VTOR`/`MSP` and jumps. With nothing bootable it blinks a fault
  indication and enters SHUTDOWN (button wake-up retries).

The product owns the slot addresses, the trusted key, the `LoaderInfo`
placement, LEDs and the loader binary/linker script. The install decision
is host-tested with simulated power loss after every flash operation; the
CC2340 SHUTDOWN entry, VTOR hand-off and flash copy on silicon are hardware
gates.

## Role images

`examples/cc2340-sensor` follows the role template (one bin per role,
mutually exclusive `sed` | `ed` | `router` features):

| bin | build | result |
|---|---|---|
| `cc2340-sensor` | default (`sed`) | unchanged |
| `cc2340-ed` | `--no-default-features --features ed --bin cc2340-ed` | builds; fallback mode 173,684 B flash, 3,684 B `.bss`; SDK mode leaves 19,940 B of stack |
| `cc2340-router` | `--no-default-features --features router --bin cc2340-router` | **link rejected** (`link/router-tables.x`) |

The router does not fit the CC2340R52's 36 KiB SRAM. Measured on the
pinned-SDK build with the default ZCL/ZDO sizes and the unmodified NWK router
tables: static RAM 32,828 B (`ZigbeeDevice<_, Router>` 22,672 B, main future
4,600 B, security journal 2,468 B, app 2,396 B, RTT 512 B), leaving 4,036 B of
stack against the 16 KiB floor (12,348 B short). Flash fits (285,524 B in the
`0x0..0x7A000` router window). The router-only growth of `ZigbeeDevice` over
the End Device is 10,824 B, less than the shortfall, so no table shrink alone
makes it fit; the options are a measured lower stack floor plus smaller
tables, or no router on this part. CI asserts the link failure in SDK mode,
because only that mode links the real radio.

Frame Pending for a future CC2340 router: the PBE acknowledges in hardware,
so the owner must be its auto-pend source-match table (`FFOPT0.AUTOPEND`,
`ENTRYENABLE`/`FRAMEPENDING` bitmaps and the PAN0 short/extended source
tables in PBE IEEE RAM), armed through `RadioPhy::set_ack_frame_pending` with
the core at `PENDING = 0`. The driver leaves the table disabled today, so
`set_ack_frame_pending` returns `Unsupported` and the parent MAC fails
explicitly. The role tags are `0x5201` (router) and `0x5202` (ED); the
router journals sit at `0x7A000..0x7E000`, below the shared security journal.

The End Device is build-, layout-, clippy- and symbol-checked only.

## Hardware status

Build and static-layout validation pass. One LP-EM-CC2340R5 board
(HWLab XDS110 + RTT + nRF 802.15.4 sniffer) has produced this evidence:

- radio bring-up (commit `03cf6d1`): Beacon Request TX and beacon RX on
  channels 11–26, association, Transport-Key, unique TCLK
  Request/Verify/Confirm-Key and a full ZHA interview with reporting
  configuration. This needed four RCL-equivalent fixes in the register-level
  driver: the PBE `SYSTIM0` start trigger, HFXT start plus the
  `HFXTCTL.HPBUFEN` radio clock buffer, `LRF_enable()` before every operation,
  and the RX FIFO SRP/RP handling;
- PBE frame filtering, hardware auto-ACK, PBE ACK wait, CCA and TX power
  (commit `f6c34a8`): over a 420 s run pending-queue drops went 32 → 0 and
  `NoAck` 6 → 0; the sniffer saw hardware ACKs 192–193 µs after the parent
  frame; a −20/0/+5/+8 dBm sweep gave sniffer RSSI −63/−43/−38/−35 dBm;
- BATMON die temperature and VDDS reported to ZHA (commit `7215c76`);
- sleepy End Device power (commits `d6a1cec`, `0ae1560`): at a 10 s poll the
  current fell from 3.5 mA to 536 µA (idle) and 7.8 µA (standby); keeping the
  LRFD images across standby brought the EnergyTrace 300 s mean to ~5.6 µA.

This is a single-board bring-up, not a qualification. All of the evidence
above was produced with the bespoke `Cc2340Mac`. Its replacement,
`SoftMacCore<Cc2340RadioPhy>`, is build-, layout- and host-tested only.

Still open:

- a hardware rerun on `SoftMacCore`:
  - join, interview, reporting, rejoin and polling;
  - Imm-Ack timing and the FP=0 auto-ACK on a sniffer;
  - delivery of a frame held in the RX FIFO after a Data Request (the faked
    frame-pending path);
  - RX FIFO head-drop and eviction under fast poll;
  - standby skipped while a frame is held;
  - ED scan;
  - 5 dBm restored after MLME-RESET;
- delivery of late parent frames from MLME-POLL (commit `edb5c12`) is
  host-tested only;
- absolute TX output power and temperature behavior;
- `LAES` hardware AES on silicon (startup self-test, secured join, reset
  and resume, behaviour after standby);
- entropy: reseed by request count and capture after standby on silicon,
  and an SP 800-90B entropy assessment of the radio noise;
- journal program/erase and reset recovery;
- the `cc2340r5-boot` loader and OTA on silicon.

Do not describe the CC2340 product as commissionable until radio
qualification is complete.
