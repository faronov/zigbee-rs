# TI CC2340R5

The LP-EM-CC2340R5 sensor is a pure-Rust Cortex-M0+ application around TI's
documented radio command interface. It imports the pinned SDK's IEEE radio
microcode/settings as data; it does not link RCL, ZBOSS, FreeRTOS, or a C
platform runtime.

## Layering

```text
environmental Sleepy End Device profile
        ↓
products/cc2340-sensor
        ↓
boards/lp-em-cc2340r5
        ↓
cc2340r5-hal (chip services + peripheral drivers)
        ↓
CC2340 register/radio mechanisms + zigbee-mac Cc2340Mac (own MacDriver, not yet on SoftMacCore)
```

`examples/cc2340-sensor` is the short composition root.

`cc2340r5-hal` owns the chip services shared by every CC2340R5 board:

- the LF RCOSC clock, VDDR regulator and standby;
- the SYSTIM Embassy time driver;
- generic IOC/GPIO `Led<DIO>` and `Button<DIO>` types;
- BATMON, factory identity, reset and the internal flash controller;
- reusable peripheral drivers: an `embedded-hal` I2C controller, the 12-bit
  ADC and LGPT PWM.

Peripheral drivers stay clock-gated until a board or product uses them.
Board crates, in-tree or out-of-tree, take these services through
`take_core()` and add only their pin map. The I2C, ADC and PWM register
sequences are host-tested against fakes but have not run on silicon.

The LaunchPad board owns:

- LED1 DIO7 and LED2 DIO6;
- Button 1 DIO13 and Button 2 DIO14;
- the typed physical LED/button resources it builds from the HAL.

The product owns the environmental profile, the BATMON-backed measurements
(die temperature, VDDS supply) plus a synthetic humidity drift, the
`Idle`/`Retention` wait policy (250 ms fast poll, 10 s slow poll), identity
strings, protected security partition, and linker layout.

The composition root maps the raw physical resources to sensor status and user
action behavior, installs RTT diagnostics, and selects reset supervision.
The board crate contains none of those application semantics.

## Application composition

```rust,ignore
SensorSedParts {
    wake,
    status,
    environment: product::environment::BatmonEnvironment::new(batmon),
    battery: product::battery::BatmonBattery::new(batmon),
    ota: NoOta,
    actions: product::policy::USER_ACTIONS,
    supervisor,
    diagnostics,
}
```

The temperature cluster reports the BATMON die temperature, not ambient
temperature; humidity is a synthetic 35–65 %RH drift until a sensor is fitted.

The image uses software AES. No production entropy source has been qualified:
`Cc2340Mac::fill_random` returns `MacError::Unsupported`
(`EntropyDisposition::UnavailableFailClosed`), so every operation that needs
local entropy fails closed. Returning a fake entropy value would make Zigbee
keys predictable, so the application does not do that.

`Idle` waits power the radio down and sleep on the SYSTIM alarm (WFE); slow
polls with `Retention` enter TI standby on the internal 32 kHz oscillator and
re-initialize the radio cores afterwards, keeping the loaded LRFD images.

## Storage

```text
0x00000000..0x0007E000  application
0x0007E000..0x00080000  SecurityStateJournal
```

The product bounds the board flash resource and constructs the journal. Flash
controller behavior remains a hardware gate.

The main task uses Embassy's compiler-sized static storage with the pinned
nightly, rather than its insufficient default 4 KiB arena. That storage is
accounted for in `.bss` before the image can link. Both copies of the product
linker layout require at least 16 KiB of stack reserve in the actual 36 KiB
SRAM region; increasing task state can no longer silently consume that reserve.
This does not qualify the radio or replace a runtime stack high-water test.

## Build

General target code uses `nightly-2026-03-23`. The release radio image requires
the exact SDK source pinned by CI:

```bash
git clone https://github.com/TexasInstruments/simplelink-lowpower-f3-sdk.git
git -C simplelink-lowpower-f3-sdk checkout \
  68ca021502383f367d0bf2a5517fdd0dcb0ef909

cd examples/cc2340-sensor
CC2340_SDK_DIR=/absolute/path/to/simplelink-lowpower-f3-sdk \
  cargo +nightly-2026-03-23 build --release --locked --target-dir target/sdk
```

With `CC2340_SDK_DIR` unset, the fallback image must compile but radio
initialization returns `FirmwareUnavailable`. This tests fail-closed behavior;
it is not a usable radio image.

The exact fallback command is:

```bash
env -u CC2340_SDK_DIR \
  cargo +nightly-2026-03-23 build --release --locked \
  --target-dir target/fallback
```

The pre-static-task pinned-SDK image measured 223,536 B against the former
225,280 B regression budget, which is no longer enforced. Its former 4,772 B
static-RAM figure included the undersized arena and was not a valid
task-capacity check. The 2026-09-10 fallback build
instead contains a 16,776 B static main-task pool, occupies 17,444 B of SRAM,
and leaves 19,420 B below the initial stack pointer. Its raw application is
213,160 B. It is still the explicit
`FirmwareUnavailable` build, not a refreshed pinned-SDK radio qualification.
The physical application slot remains 516,096 B (`0x7E000`); memory, partition,
and stack checks remain mandatory.

## Bootloader and OTA staging

Products that need over-the-air updates can keep an MCUboot-compatible
layout (for example a 16 KiB loader at `0x0`, primary and secondary slots,
and an NV region) with two reusable pieces:

- `mcuboot-image` (workspace crate, `no_std`): imgtool header/TLV parsing,
  SHA-256 + ECDSA P-256 validation, MCUboot trailer magic, the
  overwrite-only install decision with MCUboot's downgrade rule, a
  `LoaderInfo` record, and (feature `firmware-writer`) a
  `zigbee-runtime` `FirmwareWriter` that stages an image in the secondary
  slot and writes the trailer magic only on activation;
- `bootloaders/cc2340r5-boot` (standalone): the loader core. It uses the
  HAL boot profile (`default-features = false`, `take_boot()`), installs a
  pending image, validates the primary, checks the vector table, sets
  `VTOR`/`MSP` and jumps. With nothing bootable it blinks a fault
  indication and enters SHUTDOWN (button wake-up retries).

The product owns the slot addresses, the trusted key, the `LoaderInfo`
placement, LEDs and the loader binary/linker script. The install decision
is host-tested with simulated power loss after every flash operation; the
CC2340 SHUTDOWN entry, VTOR hand-off and flash copy on silicon are hardware
gates.

## Hardware status

Build and static-layout validation pass. One LP-EM-CC2340R5 board
(HWLab XDS110 + RTT + nRF 802.15.4 sniffer) has produced this evidence:

- radio bring-up (commit `03cf6d1`): Beacon Request TX and beacon RX on
  channels 11–26, association, Transport-Key, unique TCLK
  Request/Verify/Confirm-Key and a full ZHA interview with reporting
  configuration. This needed four RCL-equivalent fixes in the register-level
  driver: the PBE `SYSTIM0` start trigger, HFXT start plus the
  `HFXTCTL.HPBUFEN` radio clock buffer, `LRF_enable()` before every operation,
  and the RX FIFO SRP/RP handling;
- PBE frame filtering, hardware auto-ACK, PBE ACK wait, CCA and TX power
  (commit `f6c34a8`): over a 420 s run pending-queue drops went 32 → 0 and
  `NoAck` 6 → 0; the sniffer saw hardware ACKs 192–193 µs after the parent
  frame; a −20/0/+5/+8 dBm sweep gave sniffer RSSI −63/−43/−38/−35 dBm;
- BATMON die temperature and VDDS reported to ZHA (commit `7215c76`);
- sleepy End Device power (commits `d6a1cec`, `0ae1560`): at a 10 s poll the
  current fell from 3.5 mA to 536 µA (idle) and 7.8 µA (standby); keeping the
  LRFD images across standby brought the EnergyTrace 300 s mean to ~5.6 µA.

This is a single-board bring-up, not a qualification. Still open:

- delivery of late parent frames from MLME-POLL (commit `edb5c12`) is
  host-tested only;
- absolute TX output power and temperature behavior;
- entropy backend;
- journal program/erase and reset recovery;
- the `cc2340r5-boot` loader and OTA on silicon.

Do not describe the CC2340 product as commissionable until radio
qualification and entropy are complete.
