# CC2340R5

The CC2340 backend targets TI's 48 MHz Cortex-M0+ wireless MCU and its
2.4 GHz LRFD radio. The host-side radio implementation is Rust: it programs
the clocks, trims, synthesizer, PA, FIFOs, and PBE operations directly.

TI's official PBE/MCE/RFE firmware is still required as radio microcode data.
The project does **not** link TI RCL, ZBOSS, FreeRTOS, or a C MAC shim.

## Hardware

| Spec | Value |
|------|-------|
| Core | ARM Cortex-M0+, 48 MHz |
| Flash | 512 KB |
| SRAM | 36 KB on CC2340R52; 64 KB on CC2340R53 |
| Radio | 2.4 GHz IEEE 802.15.4 and Bluetooth LE |
| Maximum TX power | +8 dBm |
| Evaluation board | LP-EM-CC2340R5 |

The LP-EM-CC2340R5 contains a CC2340R52, so the example linker script exposes
the device's full 36 KB SRAM (`0x9000`). CC2340R53 support requires its
separate 64 KB memory layout and board-specific radio configuration.

## Architecture

```text
Cc2340Mac
   │
   ▼
Cc2340Driver
   ├── Rust MMIO clock, trim, synthesizer, and PA setup
   ├── generated TI IEEE PHY register writes
   ├── official PBE/MCE/RFE images loaded as data
   ├── LRFD FIFO access with the TI RCL-367 pointer workaround
   └── polling PBE TX/RX operations and ENDCAUSE decoding
```

The implementation is split across:

```text
zigbee-mac/src/cc2340/
├── mod.rs       # MacDriver integration and MAC primitives
├── driver.rs    # Radio lifecycle and polling TX/RX state machine
├── fifo.rs      # DataEntry encoding, FIFO access, events, RCL-367
├── hardware.rs  # MMIO bring-up, trims, PLL, PA, TOPsm cores
├── config.rs    # Generated PHY writes and board TX-power table
└── firmware.rs  # Generated PBE/MCE/RFE image access
```

## TI SDK input

Set `CC2340_SDK_DIR` to a compatible
[SimpleLink Low Power F3 SDK](https://www.ti.com/tool/SIMPLELINK-LOWPOWER-F3-SDK):

```bash
export CC2340_SDK_DIR=/path/to/simplelink-lowpower-f3-sdk
```

`zigbee-mac/build.rs` imports:

- IEEE PBE, MCE, and PLL-capable RFE firmware arrays;
- the canonical CC23xx IEEE 802.15.4 PHY JSON;
- CC23x0R5 register headers used to resolve masks and offsets;
- the LP-EM-CC2340R5 TX-power table.

The generated firmware excludes TI's leading length word and verifies that
each image fits its 4 KiB TOPsm RAM.

If the variable is absent, the crate still compiles, but
`Cc2340Driver::init()` returns `FirmwareUnavailable` or
`RadioConfigUnavailable`. This fallback is useful for source checks only.

## Build

```bash
rustup target add thumbv6m-none-eabi

cd examples/cc2340-sensor
CC2340_SDK_DIR=/path/to/simplelink-lowpower-f3-sdk \
  cargo build --release
```

The repository CI checks out a pinned subset of TI's public SDK source and
builds the same SDK-backed firmware. No TI archive is linked.

## Radio initialization

`Cc2340Driver::init()` performs:

1. the early HFXT trim workaround;
2. LRFD and radio-memory clock enable;
3. PBE, MCE, and RFE firmware loading;
4. generated IEEE PHY register writes;
5. nominal-temperature FCFG trims;
6. synthesizer and board PA programming;
7. PBE/MCE/RFE TOPsm startup and readiness polling;
8. FIFO and stale-event reset.

Initialization fails explicitly if firmware, PHY configuration, trim data, or
hardware readiness is unavailable.

## TX and RX

TX accepts an FCS-free MAC frame of at most 125 bytes. The Rust driver builds
TI's `RCL_Buffer_DataEntry` layout, adds the one-byte PHR, and asks the PBE to
generate the two-byte FCS.

RX runs the IEEE operation in promiscuous mode, reads a complete DataEntry
from the unwrapped RX FIFO, strips the PHR and FCS, and returns the MAC frame
with RSSI and link-quality metadata. CRC-error and ignored frames are flushed
by the generated PHY configuration.

### Link quality

The PBE can append an LQI byte (`FIFOCFG.APPEND_LQI`), but on CC2340 that byte
is a raw modem/frequency-offset estimate with undocumented scale and polarity —
it is **not** an IEEE 802.15.4 LQI. Feeding it to the stack would corrupt NWK
link cost (R22 §3.6.3.1) and rejoin parent selection. The driver therefore
keeps it only as optional diagnostic metadata, `RxFrame::modem_lqi`, and never
reports it as link quality.

The stack's LQI (`RxFrame::lqi`, and hence `PanDescriptor::lqi` and the
`McpsDataIndication`) is derived from the appended RSSI instead, once, via the
shared `zigbee_mac::lqi::from_rssi_dbm` policy. RSSI is mandatory: a FIFO entry
without usable RSSI never produces a frame, because a fabricated `lqi = 0`
would be indistinguishable from a genuinely dead link. The two ways that can
happen are deliberately handled differently:

| FIFO condition | Meaning | Driver behaviour |
| --- | --- | --- |
| RSSI is TI's invalid sentinel (`0x7F`) | per-frame: this entry has no reading, the next one may | the entry is **dropped** (it is already consumed from the FIFO) and the continuous RX operation keeps running; logged at `debug`, escalated to a single `warn` after 8 consecutive drops |
| `FIFOCFG.APPEND_RSSI` is clear | the runtime FIFO configuration is broken; *every* frame will fail identically | `RadioError::LinkQualityUnavailable`, aborting the operation — dropping here would spin forever while silently receiving nothing |

Dropping matters for correctness, not just tidiness: `receive()` backs an
active scan, an association response wait and a rejoin response wait. Returning
an error for a single bad frame truncated all three, so one unusable beacon
could hide the parent the device needed. `classify_rx_fifo_error` is the single
place that decision is made, and it is unit-tested so a refactor cannot make
the per-frame case terminal again.

The RSSI→LQI curve is this stack's initial estimate policy, shared with the
EFR32/EFR32S2/PHY6222 backends, and still needs per-radio PER-vs-RSSI
calibration on hardware before it can be called production-accurate.

FIFO pointer changes use the same protected sequence as TI RCL:

1. disable CPU interrupts;
2. redirect PBE FIFO commands from `FCMD` to `FSTAT`;
3. perform two dummy reads;
4. update the pointer;
5. restore `FCMD`;
6. restore the previous interrupt state.

The current implementation polls doorbell events and cooperatively yields to
the async executor. IRQ-driven completion is a later optimization.

## Example limitations

`examples/cc2340-sensor` is still a bring-up example, not production firmware:

- the Embassy time driver is a zero-returning compile stub;
- IOC setup, button pull configuration, and complete board initialization
  still need a CC2340 HAL or verified register setup;
- CCA and hardware auto-ACK are not implemented;
- no CC2340 target has been flashed or tested on air.

The low-level TX/RX driver no longer depends on the example time stub, but the
full Zigbee application uses timers and therefore needs a real RTC or SysTick
Embassy time driver before hardware testing.

## Flashing

Use TI UniFlash with the LP-EM board's XDS110 probe. `probe-rs` can also be
used when the installed target database supports the exact CC2340R5 variant.
