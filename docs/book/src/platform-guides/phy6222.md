# PHY6222 / PHY6252

The PHY62x2 802.15.4 driver (`zigbee-mac/src/phy6222`) and the end-device
MAC path are hardware-proven on the Ai-Thinker PB-03F-Kit (PHY6252), see
[PB-03F-Kit](#pb-03f-kit-phy6252). The default PHY6222 environmental sensor
and the PHY6252 feature-selected EVK build are compile- and layout-tested
only; their ROM boot, flash and power paths are not hardware-proven.

## Layering

```text
environmental Sleepy End Device profile
        ↓
products/phy62x2-evk
        ↓
boards/phy62x2-evk
        ↓
phy6222-hal + SoftMacCore<Phy6222RadioPhy>
```

`examples/phy6222-sensor` is the short composition root.

The product owns identity, profile, battery/poll policy, protected partition,
and ROM-aware linker layout. The board owns physical wiring and whole-device
flash. The shared `SensorApp` owns commissioning, polling, reporting, and
persistence checkpoints.

## Application behavior

The current product uses:

```text
fast wait: Idle
slow wait: Idle
sample interval: 30 s
slow parent poll: 10 s
OTA: NoOta
```

`PhyWakeController` uses the real Embassy SysTick monotonic, radio sleep, and a
timer/button wait. It explicitly rejects `Retention`.

The product selects centralized Trust Center commissioning and does not
provision a distributed-security key. Distributed commissioning is therefore
compiled out and a persisted distributed network is rejected. Its single
application endpoint does not expose the Groups cluster, so the build also
uses the compact endpoint/reporting capacities and omits the Groups-to-APS
mutation bridge. Other products retain those capabilities through their
default features.

The HAL contains AON RTC, retention, and RAM-resident entry primitives, but the
production example does not use them. No AON sleep current or battery-life
number is published.

## ROM image and memory

```text
ROM IRQ jump table: 0x1FFF0000..0x1FFF03FF
ROM-owned SRAM:     0x1FFF0400..0x1FFF1837
run descriptor:     0x1FFF1838
XIP application:    0x11010100..0x1103DADF (+ image tail <= 0x1103DFFF)
PHY6 image header:  flash offset 0x10000, size 0x100
```

The application slot is hard-gated at 187,104 bytes (`0x2DAE0`):

| feature image | occupied XIP span | hard XIP gate | result |
|---|---:|---:|---:|
| PHY6222 (default) | 138,624 | 187,104 | 48,480 bytes free |
| PHY6252 (`--no-default-features --features phy6252`) | 138,624 | 187,104 | 48,480 bytes free |

These are local `nightly-2026-08-01` macOS cross-build measurements (text +
rodata + data). The slot runs from 0x10100 up to the PHY6252 security
partition at 0x3E000 (0x2DF00 bytes) minus 0x420 bytes reserved for the
segments `phy62x2-image` appends after the XIP data (IRQ jump table, run
descriptor, padding and CRC), so the packaged image can never reach the
journal. Nothing else lives between the image end and 0x3DFFF for the EVK
(no OTA bank). A linker `ASSERT` and a CI check of the packaged `phy6.bin` end
enforce both bounds; in the same local build both packaged images end at
0x32274. The target-local `--icf=all` linker option folds
identical functions without changing features, software AES, or physical
boundaries. Identical functions may share addresses; function-address
uniqueness is not an identity contract. The flash-operation path must still
pass the SRAM checks.

Release builds use the nightly `immediate-abort` panic strategy, set in
`examples/phy6222-sensor/.cargo/config.toml`. Every panic site is a single
`udf` trap: the core enters the cortex-m-rt default `HardFault` handler and
halts there, as `panic-halt` did, but with lower-priority interrupts stopped
and the faulting PC identifying the panic site. This saves 3,328 bytes of
panic arguments, `Location` records and `core::panicking` calls. SRAM
placement and size are unchanged.

Linux CI and hardware qualification remain separate gates. The packaged PHY6
file includes loader metadata and is not the gate metric.

The ELF is not directly flashable. The PHY6 packager retains the ROM loader's
segment information.

## Persistence

| product | security journal |
|---|---|
| PHY6222, 512 KiB | `0x0007E000..0x00080000` |
| PHY6252, 256 KiB | `0x0003E000..0x00040000` |

The shared `SecurityStateJournal` is backed by RAM-resident flash operations
with bounded SPIF waits. The implementation pauses SysTick and accounts for
the interval through the AON RTC so flash work does not make monotonic time
run slow. These guarantees are host/target-compiled, not yet proven through
power interruption on silicon.

## Build and package

Use `nightly-2026-08-01`:

```bash
cd examples/phy6222-sensor
cargo +nightly-2026-08-01 build --release --locked
```

Package the default PHY6222 image:

```bash
ELF=target/thumbv6m-none-eabi/release/phy6222-sensor
OBJCOPY=$(find "$(rustc +nightly-2026-08-01 --print sysroot)" \
  -name llvm-objcopy -print -quit)
"$OBJCOPY" -O ihex "$ELF" "$ELF.hex"
sh check-layout.sh "$ELF"
cargo +nightly-2026-08-01 run --quiet --locked \
  --manifest-path ../../Cargo.toml -p phy62x2-image -- \
  "$ELF.hex" "$ELF.phy6.bin"
```

Cross-build the exact PHY6252 feature image:

```bash
cargo +nightly-2026-08-01 build --release --locked \
  --no-default-features --features phy6252
```

This PHY6252 feature build fits the same XIP gate (see above); its complete
hardware path remains unverified.

## PB-03F-Kit (PHY6252)

`boards/pb03f-kit` (wiring), `products/pb03f-kit` (identity, layout,
policy, journal) and `examples/pb03f-kit` (composition roots) target the
Ai-Thinker PB-03F module: PHY6252 QFN32, 512 KiB flash (JEDEC `0x1340C4`),
64 KiB SRAM.

| function | pin |
|---|---|
| RGB LED red / green / blue | P7 / P11 / P18 |
| cool-white / warm-white LED | P34 / P0 |
| user button (active low) | P15 |
| UART0 to CH340, 115200 8N1 | P9 TX / P10 RX |
| SWD | P2 / P3 (never remuxed; no I2C fitted) |

Binaries: `pb03f-zigbee` (end device with a synthetic temperature/humidity
series, idle wait, no AON sleep, no OTA), `pb03f-lab` (GPIO/UART/flash/ADC
bring-up) and `pb03f-radio-lab` (raw 802.15.4 beacon-request/scan lab with a
software/hardware FCS A/B switch).

There is no second-stage bootloader. `phy62x2-image --rom-boot` turns the
ELF into two flash regions so the factory sectors are never erased:

```text
0x02000  <elf>.table.bin  boot-ROM application table (4 KiB)
0x03000  factory boot/OTA record, 0x4000 BLE public address  (preserved)
0x05000  <elf>.app.bin    SRAM load data, then XIP text from 0x10100
0x10100..0x40FFF          XIP slot (200,448 B)
0x41000..0x7DFFF          reserved for OTA staging (unused, 244 KiB)
0x7E000..0x7FFFF          security journal
```

Battery: the kit has no battery or divider, so the product reports the
module supply. P14 (ADC channel `CH2P`) is driven high while the ADC samples
it in auto mode with the 3.2 V attenuator, so the reading is VDD through the
pad, scaled by the SDK's nominal QFN32 lambda (uncalibrated, no per-chip
efuse correction). The product curve is the EVK's 2.0–3.0 V linear curve and
the Power Configuration descriptor advertises 2 × AA (1.5 V rated), the
supply class this module would run from on batteries. On USB (3.3 V LDO) the
kit reads 3,305–3,308 mV. The HAL clears `CLKHF_CTL1` bit 21 for the ADC
clock as THB2 does; the SDK `hal_adc_config` value (`[21:20] = 1`) left the
PB-03F ADC without a clock (no conversion completed). `Adc::new` powers the
ADC down because `PCRM` keeps its enable bits across warm and debug resets.

The EUI-64 is derived from the factory BLE address at `0x4000`. Program the
app before the table with a probe that uses the boot ROM's SPIF routines (the
generic `PHY6222` J-Link flash loader erased the whole device in testing; use
the `Cortex-M0` core). The CI job `build-pb03f` builds all three binaries,
runs the layout check with `XIP_SLOT_BYTES=200448` and uploads the images.

Hardware evidence (PB-03F-Kit, ZHA network on channel 15, independent nRF
sniffer):

- ROM boot, `LL_IRQ` dispatch, TP/DCOC calibration, beacon request/scan;
- software and hardware FCS both accepted on air (70/70 frames FCS-OK);
  the LL engine's hardware FCS is the default (`FcsMode::Hardware`), and
  `FcsMode::Software` stays selectable through `RadioConfig`;
- association, ACK turnaround (TRX ACK wait, SRAM interrupt-context ACKs), data
  polling and addressed RX/TX;
- secured commissioning, unique TCLK exchange, End Device Timeout, ZHA
  interview, configured reporting, Read Attributes;
- journal writes and resume after reset without re-commissioning;
- with hardware FCS as default: 867/867 device-sourced frames FCS-OK in a
  240 s capture, plus 8/8 of its interrupt-context ACKs (matched by sequence
  number);
- supply ADC: `Battery { millivolts: 3306, percentage: 100 }` on UART; ZHA
  reads `BatteryVoltage` = 33 (3.3 V), `BatteryPercentageRemaining` = 200,
  `BatterySize` = AA, `BatteryQuantity` = 2.

ACK turnaround: the LL engine has no 802.15.4 address filter, ACK template
or frame-pending logic (none in `ll_hw_drv.h`, the ROM symbols or the SDK),
so the driver acknowledges from the radio interrupt, like the SDK's
proprietary-PHY auto-ACK (`phy_plus_phy.c` `phy_rf_txack`). The part of
`LL_IRQ` up to the ACK trigger runs from SRAM without calls into XIP, and the
ACK's TX baseband delay (`RF+0xBC`, `ll_hw_set_trx_settle`) is tuned to the
12-symbol aTurnaroundTime. Sniffer results (ACK start versus the other
children of the same parent, 200 s captures with ZHA reads):

| Build | Turnaround | Parent frames ACKed | Parent retransmissions |
| --- | --- | --- | --- |
| Before (ACK path in XIP) | ≈450 µs (190–550) | 14 of 20 | 6 |
| SRAM handler, hardware FCS, BB 118 µs (default) | ≈192 µs, ±1 µs | 12 of 12 (twice) | 0 |
| SRAM handler, software FCS, BB 127 µs | ≈170 µs, ±1 µs | 12 of 13 | 1 |

Software FCS starts the ACK ~31 µs earlier for the same delay, and a 149 µs
delay suppressed the ACK entirely, so that mode stays at the vendor's 127 µs
ceiling. A later re-measurement (120–200 s captures, hardware FCS) put both
the pre-port build (157d189) and the `SoftMacCore` build at ≈161 µs, ±1 µs,
11 of 11 ACKed, 0 retransmissions. The sniffer also splits third-party ACKs
into the same two classes ~31 µs apart, so the 161/192 µs difference is not
attributed to the port; its cause is not identified. ACKs always carry `frame pending = 0` (end-device-only backend). The
PB-03F console logger keeps interrupts enabled while writing, and SysTick
runs at the lowest priority, so neither delays the radio interrupt. Still
open: the radio is not re-armed while the task processes a received frame,
so a parent retransmission arriving during that window is not ACKed.

MAC: the shared `SoftMacCore` (scan, association, poll, CSMA-CA, retries)
over `Phy6222RadioPhy` (`TxOffload::AckWait`: the LL engine's TRX operation
receives the Imm-Ack; `hardware_auto_ack`: the SRAM `LL_IRQ` sends it). The
port to `SoftMacCore` is hardware-checked on the PB-03F: resume after reset,
ZHA Read Attributes (12 of 12) and reports, sniffer 11 of 11 ACKs FCS-OK with
0 parent retransmissions.

XIP use of `pb03f-zigbee`: 196,320 of 200,448 bytes (564 bytes of the radio
interrupt run from SRAM). The slot grew by one 4 KiB sector (from 196,352 B)
for the shared MAC; see the approved PHY62x2 exception in
[Firmware size](../advanced/firmware-size.md#mac-unification-footprint-baseline).

## Hardware gates

Proven on PB-03F-Kit only (above). Still open on every board:

- journal power-interruption recovery;
- AON sleep, wake restoration, and measured current;
- OTA;
- the EVK products' ROM boot and flash path, and the EVK P11 supply divider
  reading (the ADC driver itself is proven on PB-03F only).
